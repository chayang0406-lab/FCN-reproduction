# CSV→h5 内存实测与 t4 风险判定（2026-11-18，captain 实测）

> 结论：**内存够，但余量不宽裕。** 4584 万行一次性读入峰值约 **44 GB**，
> 上限 115 GB，占 38%。可以一次读入，但要守住下面三条纪律，否则叠加后会爆。

## 一、实测数据（不是估算）

方法：**每一档行数起一个全新子进程**，用 `ru_maxrss` 读该进程历史峰值 RSS
（这才是 OOM killer 看的东西）。用 `dtype=object`（fuxictr 的 `read_csv` 就是这么读的）。

| rows | 峰值 RSS | 字节/行 |
|---|---|---|
| 50,000 | 149.8 MB | 3,142 |
| 100,000 | 211.7 MB | 2,220 |
| 200,000 | 332.8 MB | 1,745 |

线性拟合：`peak(MB) = 0.00121867 × rows + 89.3`，**R² = 0.99997**（线性性成立）

外推全量 36,672,493 行 → **约 43.7 GB**（占 114.97 GB 上限的 **38%**）

## 二、⚠️ 我第一版测量方法错了，这个教训要记住

初版在**同一进程内**循环测多档，用「读完 RSS − 读前 RSS」当增量。
结果 R²=0.0009（几乎零相关），且 200k 行的增量**比 100k 行还小**。

根因：**pandas/glibc 释放的内存不还给 OS**，下一轮复用了已分配的 arena。
所以那个「差值」既不是峰值、也不是真实占用，外推会得出「全量只要 0.5 GB」这种荒谬结论。

**修正做法：每档独立子进程 + `ru_maxrss`（历史峰值）**。R² 从 0.0009 变成 0.99997。

> 这正是本项目反复强调的方法论纪律：**用拟合下结论必须多点多档验证，
> 且要先看 R²；R² 不合格时拟合结果一律作废，不能拿去做外推。**

## 三、另一个认知偏差：纸面估算比实测高 2.4 倍

我按「每个 Python str 对象 49 字节头部 + 内容 + 8 字节指针」纸算，得出约 **103 GB**（接近上限，判定高风险）。
实测只有 **44 GB**（每行 1,278 字节 ≈ 40 列 × 32 字节）。

差异原因：CPython 对不同长度的 str 有 intern/SLAB 复用，且短字符串（大量重复的
`C` 字段十六进制值）会被共享，实际远低于「每格一个独立对象」的纸面模型。

**教训：内存这类底层开销，纸面估算误差可达 2 倍以上，必须实测。**

## 四、t4 可以一次读入，但必须守三条纪律

### 纪律 1：不要同时持有 object 版和 int 版
`preprocess()` 会做 `astype(int)`，若原 object DataFrame 未释放，峰值会接近 44 + 12 = 56 GB。
虽然仍在 115 GB 内，但要确保 `del train_ddf; gc.collect()` 及时执行
（fuxictr 的 `build_dataset` 里有这一步，但要确认它真的在 transform 后才释放）。

### 纪律 2：只用 6 核 CPU 配额，别开高并发
`transform_h5` 若 `block_size > 0` 会用 `mp.Pool(cpu_count() // 2)`。
宿主机报 32 核，但 **cgroup 配额只有 6 核**——开 16 个进程会严重超卖、互相拖慢，
且**每个子进程可能各自持有一份数据副本**，内存会成倍上涨。

**建议：`data_block_size=0`（单进程，不用 Pool）**，牺牲一点速度换内存安全。

### 纪律 3：转换期间不要跑别的重活
E0 训练也在同一台机器上。h5 转换（44 GB）+ 训练（约 3-5 GB 显存 + 若干 GB 主机内存）
同时跑，要注意主机内存叠加。**建议串行：先转完 h5，再开训练。**
