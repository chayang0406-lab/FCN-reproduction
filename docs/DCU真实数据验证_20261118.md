## 二、这次验证排掉的两个远程专属雷

### 雷 1：`model.fit()` 不能显式传 `epochs=`
`fuxictr` 的 `fit(self, data_generator, epochs=1, validation_data=None, **kwargs)`，
而 `params` 字典里**已经含 `epochs` 键**（来自 config）。写成
```python
model.fit(tr, validation_data=va, epochs=3, **params)   # ← 报错
```
会 `TypeError: fit() got multiple values for keyword argument 'epochs'`。
正确写法：
```python
params["epochs"] = 3
model.fit(tr, validation_data=va, **params)
```

### 雷 2（重要，会影响所有日志解析）：fuxictr **只在第一个 epoch 打 `start`**
日志长这样：
```
Epoch=1 start
Epoch=1 end
Epoch=2 end      ← 没有 "Epoch=2 start"！
Epoch=3 end
```
实测：`starts=1`，`ends=19`（作者日志）或 `ends=3`（我们的）。

**所以任何「用 start 时间戳差分算 epoch 耗时」的代码都会静默算错**（算出 0 个或 1 个值）。

正确算法：
```python
epoch1 = end1 - start1
epochN = endN - end(N-1)      # N >= 2
```

> 这个坑我第一次写解析时就踩了，算出来 `epoch_seconds: []`（空列表），
> 而结果 JSON 里只是静默为空，**不报错**。差点让「实测 epoch 时间」这项变成空的还浑然不觉。

已用正确算法复核作者日志：**19 个 epoch，均值 191.2 s/epoch**（范围 189.1–192.9），
与此前报告的「约 191 秒」一致 —— 结论没变，但方法原来是错的。

## 四、待补：真实全量下的 s/epoch

**真实 s/epoch 必须等 4GB 全量数据到位后跑完整 epoch 才有意义。**

- **建议按 11 小时排**
