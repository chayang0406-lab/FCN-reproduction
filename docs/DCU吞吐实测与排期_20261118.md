# DCU 训练吞吐实测与排期结论（2026-11-18）

> 这是决定「实验能做多少个种子」的关键数字。captain 亲自在 DCU 上实测，
> 因为 infra 当时报的 4.37 s/batch 是冷启动含 JIT 编译，不能用。

## 一、结论先说

**DCU K500SM_AI 与论文用的 RTX 4090 基本同一量级，只慢 1.26 倍。**
所以原计划的「7 个随机种子」方案**时间上完全可行**，不需要缩减。

| 指标 | 实测值 |
|---|---|
| 稳态单 batch 耗时 | **0.0511 秒** |
| 推算 s/epoch（4477 batch） | **228.6 秒（3.81 分钟）** |
| 论文 RTX 4090 FCN𝑝 参考 | 182 秒 |
| DCU / 4090 慢倍数 | **1.26×** |
| 单种子 20 epoch | 约 **76 分钟** |
| **7 种子全流程** | 约 **8.9 小时** |

## 二、怎么测的（可复跑）

脚本：`tools/bench_dcu_throughput.py`（远程同名）

关键设计要点，缺一个数就不可信：
1. **用作者日志里的真实 vocab 尺寸**（39 个字段，合计 910,747），
   而不是随便造小 vocabulary。因为 embedding 表大小直接影响参数量
   （14.5M vs 几百万）和 Adam 的更新开销。
2. **实测参数 = 16,532,562**，与闭式公式算出的 HEAD 默认配置值**完全一致**
   → 说明台架搭对了，测的是真模型。
3. 预热 40 个 batch 丢弃，再测 120 个 batch 取平均，
   避开 kernel 首次编译（JIT）的污染。
4. 走 `model.train_step()` 真实路径（含 `clip_grad_norm_`），
   不是自己重写前向反向。

## 三、踩到并绕过的两个坑（留给后人）

### 坑 1：`train_step` 不能在 `fit` 之外单独调用
fuxictr 2.0.1 的 `BaseModel.__init__` **没有**初始化 `_max_gradient_norm`，
它只在 `fit()`（第 139 行）里被赋值；而 `train_step()`（第 195 行）要读它。
直接调用会 `AttributeError`。

**绕法**（一行，不改 fuxictr 源码）：
```python
model._max_gradient_norm = 10.0
```
infra 另做了静态调用链分析确认：`train_step → get_total_loss → add_loss`
这条链上**只有** `_max_gradient_norm` 这一个属性缺失，其余
（`_embedding_regularizer`、`_net_regularizer`）都已在 `__init__` 就绪；
而 `_best_metric`、`_epoch_index`、`_total_steps` 等虽然也只在 `fit` 里赋值，
但 `train_step` 根本不读它们。

**不要用 `fit()` 来顺带初始化**——它会执行 `load_weights(self.checkpoint)`，
bench 环境没有 checkpoint 会炸另一个错。

### 坑 2：`FeatureMap.load` 的 features 格式
fuxictr 2.0.1 期望 `features` 是 **「每项只有一个键的 dict」组成的 list**：
```python
"features": [ {"C1": {...}}, {"C2": {...}}, ... ]
```
而不是一个大 dict。写成大 dict 会报
`AttributeError: 'str' object has no attribute 'items'`。

### 坑 3（非阻塞）：dataloader 会被耗尽
`H5DataLoader` 一个 epoch 就结束。要测 N 个 batch 就得保证
`n_train >= (warmup + measure) × batch_size`，否则中途 `StopIteration`。

## 四、这个数字的适用边界（别过度解读）

**它偏乐观，正式数字必须用真实 Criteo 数据重测。** 原因：
1. 合成数据的 embedding 更新是**稠密全表**还是**稀疏行**取决于实现，
   真实数据下 910,747 个 ID 的稀疏访问模式与合成数据不同。
2. **不含每 epoch 的 validation evaluation**。作者的 182/191 秒是含 eval 的
   （日志里 eval 一个 epoch 要 ~12 秒）。
3. 合成数据是均匀随机 ID，缓存命中率比真实长尾分布更友好。

**所以：**
- 用它做**排期决策**（够不够时间跑 7 个种子）→ 够用，且有余量。
- 用它写**报告的「每 epoch 秒数」** → 不行，必须换成真实数据实测值。

## 五、顺带的发现：当前是 kernel 启动开销主导，不是算力瓶颈

infra 的 batch_size 扫描（合成数据）显示单步耗时几乎不随 batch 变化：

| batch_size | 单步(s) | samples/s |
|---|---|---|
| 512 | 0.0312 | 16,411 |
| 2048 | 0.0319 | 64,107 |
| 8192 | 0.0336 | 243,584 |

batch 差 16 倍而单步时间只差 8% → 说明 DCU 大部分时间在等 kernel 启动，
算力没吃满。**对实验的含义：batch 越大越划算，用作者的 8192 是合理的。**
这点可以写进报告的「效率分析」，是个真实的观察。

## 六、排期落地

按 228.6 s/epoch、20 epoch 早停/种子算：

| 实验 | 种子数 | 预估耗时 |
|---|---|---|
| E0 基线 FCNv2 | 7 | 8.9 h |
| E3 改进（Tri-BCE 软权重） | 5 | 6.4 h |
| E4-A 消融（w/o E2L、w/o L2E、w/o Tri-BCE） | 各 1–2 | 3.8–7.6 h |
| E4-B LCA 压缩率扫描（r=1/2,1/4,3/4,1） | 各 1 | 3.8 h |
| **合计** | | **约 23–27 h** |

时间够，但要注意：
- 6 核 CPU 配额下**不要并行跑多个训练**，会互相抢核反而更慢。
- 端口/长任务用 `nohup` 后台跑，结果落盘。
- 服务器是共享盘（只剩 168G），**所有实验共用同一份 h5**，不要各建一份。
