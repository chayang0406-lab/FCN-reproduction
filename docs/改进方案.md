## 1. 改动一：Tri-BCE 权重软化

### 1.1 原版在做什么（先讲人话）

FCNv2 里有两个"单塔"和一路"合体"：

- `E2L` 支路单独给出的预测 → `y_d`
- `L2E` 支路单独给出的预测 → `y_s`
- 两路平均 → `y_pred`（真正用来预测的）

原版训练目标（`src/FCNv2.py` 第 83-90 行）：

```
loss = L(y_pred, y)
Δ_d  = L(y_d, y) - L(y_pred, y)          # 单塔比合体差多少
Δ_s  = L(y_s, y) - L(y_pred, y)
w_d  = max(0, Δ_d)                        # 差就罚，好就不罚
w_s  = max(0, Δ_s)
loss = loss + L(y_d,y)·w_d + L(y_s,y)·w_s
```

用人话说：**"哪个单塔比合体预测差，就额外罚它一下，罚的力度等于差多少。"**
这叫 Tri-BCE（三路二元交叉熵），是 FCN 的组件之一。

### 1.2 为什么这是个问题

`max(0, ·)` 有两个毛病：

**毛病一：拐角不可导。** 在 Δ=0 处，左边的梯度是 0，右边的梯度是 1。训练时这一步的梯度会突然跳变，
损失曲线上出现小毛刺。这不算致命，但目标函数不光滑本身不优雅。

**毛病二（更重要）：死区。** Δ<0 时 `w=0`，而 `w=0` 意味着 `L(y_d,y)·w_d` 这一项对参数的梯度**恒为 0**。
于是那个单塔再也拿不到"额外的监督信号"——**哪怕它后来变好了，也不会被重新纳入惩罚**。
它是一个单向的开关：一旦关上，就再也打不开。

这一点值得用具体数字说：`[实测]` 在 Δ=-1e-6 处，`relu'(Δ)=0`，而我们的 `smoothmax'(Δ)=0.5`。
差的不是数值大小，是**有没有梯度**。

### 1.3 三种软化方案

| 模式 | 公式 | 特点 |
|---|---|---|
| `hard` | `max(0, Δ)` | 原版。Δ<0 时梯度为 0 |
| `softplus` | `α·softplus(βΔ)/β` | β→∞ 时**收敛到原版**；但含常数偏置 `log2/β` |
| `smoothmax` | `α·Δ·sigmoid(βΔ)` | 把拐角磨圆且**无常数偏置**，推荐作为主改进 |
| `ratio` | `α·Δ/(L_aux+L_main)` | 量纲无关；**可能为负**（单塔更好时反而加权），需 `clamp_nonneg` 才稳 |
| `plain` | 去掉两个辅助项 | 普通 BCE，对应论文消融的 w/o Tri-BCE |

**为什么 `softplus` 是"原版的极端情形"（这点值得讲）**：
`softplus(βΔ)/β → relu(Δ)` 当 β→∞。所以原版不是"另一种方法"，而是**软权重把硬度旋钮拧到无穷大**。
这让改动有了连续性——不是换目标函数，是调一个温度参数。

**为什么必须有 `smoothmax`（这是实测发现的，不是纸上推的）**：
`softplus(βΔ)/β = relu(Δ) + log(2)/β + O(Δ²)`。中间那个 `log(2)/β` 是**与 Δ 无关的常数偏置**。

- Criteo 上损失约 0.436，`Δ = L_aux - L_main` 的典型量级只有 1e-4 ~ 1e-3 `[论文+推断，见 §7 待测]`
- 若取 β=1，`log(2)/1 = 0.693` —— **比 Δ 本身大三个数量级**
- 结果：软权重恒等于 ~0.69，等于"不管单塔好坏都狠狠加权"，训练必然崩

`[实测]` 见 `test_A2`：Δ=0 处 softplus(β=1) = 0.693，smoothmax = 0.0。
所以 `softplus` 必须把 β 调到 1e3~1e4（配置文件里用 1e4，残余偏置 6.9e-5），
而 `smoothmax` 在 β=100 就能用。**这是选 `smoothmax` 作为主实验的唯一理由，不是偏好。**

### 1.4 退火

`w_k = w · [floor + (1-floor)·exp(-λk)]`，k = 已完成 epoch 数。

- 人话：一开始用完整强度，越往后越接近"不加权"。
- 理由：辅助项的价值主要在训练早期（帮两个单塔尽快成形）；后期合体与单塔已差不多好，
  再使劲加权只会拖累收敛。
- **实现上不改框架**：直接读 `BaseModel` 已有的 `self._epoch_index`（`fit()` 每轮更新它），
  取不到时按 k=0。λ=0 且 floor=0 时 `_anneal_decay()` **精确返回 1.0**，完全不进乘法分支，
  因此"不退火"对数值零影响 `[实测，test_A5]`。

## 2. 改动二：LCA 压缩率参数化

### 2.1 原版在做什么

每个交叉层（`src/FCNv2.py` 第 132 行起）：

```python
w[i]  = nn.Linear(D, D // 2, bias=False)     # D = input_dim = 624
H_1   = w[i](x)                               # 宽 d = D/2 = 312
H_2   = γ ⊙ H_1 + β                           # 宽 d（逐元素仿射）
H     = cat([H_1, H_2])                       # 宽 d + d = 624 == D
x     = x_anchor ⊙ (H + b[i]) + x             # b 宽 D；残差流宽度恒为 D
```

**关键观察：那个 `//2` 不是随手写的。**

`H_2` 是 `H_1` 的逐元素仿射变换，所以 `H_2` 的宽度**必然等于** `H_1` 的宽度 `d`。
拼起来宽度是 `2d`。要接上残差 `(H + b)`（`b` 宽 `D`），必须有 `2d = D`，即 `d = D/2`。

**换句话说：砍半不是为了省参数，是为了让拼接后的宽度恰好等于 D。**
`[实测]` 见 `tools_check_lca.py`：取 d=D/4=156，拼接后宽 312 ≠ 624，加 `b` 直接形状报错。

### 2.2 怎么参数化（以及为什么不能用"两个投影"）

把 `r` 引入后 `d = rD`，拼接宽度 `2rD` 一般 ≠ `D`，必须显式调回来。三种做法：

| 做法 | r=1/2 时是否与原版逐位一致 | 参数量是否只随 r 变化 |
|---|---|---|
| **A. 单一投影 + 零参数宽度适配器**（本项目采用） | **是**（适配器退化为恒等，零算子） | 是 |
| B. 两个独立投影 `w1: D→d`, `w2: D→(D-d)` | **否**，结构里多了一个矩阵 | 是，但基数不同 |
| C. 截断/补零硬凑 | 是 | 会丢信息或引入死坐标 |

做法 B 看起来很优雅（拼接后天然等于 D，不需要适配器），但 `[解析，tools_check_lca.py]` 证明它不可用：

- r=1/2 时每层参数 391,248，而原版是 195,936 —— **正好是 2 倍**
- 也就是说 r=1/2 的"基线"已经不是原版，A/B 对照失去基准
- 且 r=1 时 `d=D`，第二个投影 `D→0` 宽度为 0，需要特判

**采用做法 A**：适配器零参数，三种情形

- `2d == D` → **恒等，一个算子都不做**（r=1/2 走这条，这是逐位一致的技术前提）
- `2d < D` → 沿最后一维平铺（tile）后截到 `D`：把压缩后的交互信号广播回 D 个坐标
- `2d > D` → 零填充到整数倍再按组求和（fold）折回 `D`：把过完备信号聚合回 D 维

适配器写成 `bool` 标记 + 普通函数（不是 `nn.Module`），因此**不进 `state_dict`、不加参数、不消耗随机数**。
参数量严格只由 `d` 决定，参数量-AUC 曲线才有干净的自变量。

### 2.2b r=1 走独立的「全秩」路径（不带 γ/β）—— 与论文对齐的必然结论

> ⚠️ 这一节是实现里**唯一一处结构不连续**，也是被 analyst 抓出来后修正的。

**判决过程**（用 4 层这个最能判别的数据点，层数少、γ/β 份额相对更明显）：

| 计算方式 | ECN-full（4 层） | 两位小数 | 论文写 | 判定 |
|---|---|---|---|---|
| 带 γ/β（把 LCA 公式代 r=1） | 4×391,248+625 = 1,565,617 | **1.57M** | 1.56M | ✗ 排除 |
| **不带 γ/β（全秩）** | 4×390,000+625 = **1,560,625** | **1.56M** | 1.56M | ✓ |

9 层同样指向"不带 γ/β"：

| 计算方式 | FCN𝑝-full（9 层） | 两位小数 | 论文写 | 判定 |
|---|---|---|---|---|
| 带 γ/β | 9×391,248+625 = 3,521,857 | 3.52M | 3.51M | ✗ |
| **不带 γ/β** | 9×390,000+625 = **3,510,625** | **3.51M** | 3.51M | ✓ |

**语义上也自洽**：LCA 论文原话是「introduce a low-cost affine transformation **to maintain consistency
with the original output dimension**」——γ/β 是**砍半后补偿维度/表达能力**的配套件，全秩时不存在维度不一致，
自然不需要它。这直接对应原仓库 `ECN_full.py` 的 `ExponentialCrossNetwork`：
每层只有 `w(D→D) + b(D)`，没有 γ/β，也不做 concat。

**所以 r=1 不是「LCA 取 r=1」，而是另一条代码路径（真全秩）：**

```python
if self.full_rank:                       # r == 1
    H = self.w[i](x)                     # w: D→D，无 γ/β、无 concat
else:                                    # r < 1，LCA
    H_1 = self.w[i](x)                   # w: D→d
    H_2 = γ[i]*H_1 + β[i]                # 补偿仿射，宽 d
    H   = cat([H_1, H_2])                # 宽 2d，r=1/2 时 == D
    if need_resize: H = resize_last_dim(H, D)   # r≠1/2 时零参数适配
x = x_anchor * (H + self.b[i]) + x
```

**这个结构不连续必须如实声明**：r ∈ {1/4, 1/2, 3/4} 是 LCA 结构（带 γ/β + concat + 可能带适配），
r=1 是全秩结构（无 γ/β、无 concat）。所以严格说，**"参数量随 r 单调变化"跨过 r=1 时换了结构**，
报告里不能把四个点当成同一条连续曲线上的四个采样。

**改完后 r=1/2 仍与原仓库逐位一致**（`test_bit_exact.py` 4/4 通过）——全秩分支只在 `r==1` 时触发，
默认 `r=0.5` 根本不进这个判断。

### 2.3 参数量（`[实测]`，与解析式完全对账）

两套解析式，分界在 r=1（理由见 §2.2b）：

```
r < 1（LCA 结构）  每层 = D·d + 2d + D      d = r·D，含 γ/β
r = 1（全秩结构）  每层 = D·D + D          无 γ/β、无 concat
末尾统一          + (D + 1)                fc 的权重 + 偏置
交叉网络 = L × 每层 + (D+1)，L = exp_num_layers + lin_num_layers
```

**两条必须分开写的口径**（否则会被判为夸大）：

- **单条交叉网络**：r=1/2 → r=1 是 `980,305 → 1,950,625`（5 层），比值 **1.9898**
  —— **不是 2.00**。根因：LCA 单层 `D·d+2d+D`，全秩单层 `D·D+D`，
  分子分母里的 `+D`（b）与 `+2d`（γ/β）不能完全约掉，所以比值严格小于 2。
- **模型总参数**：5 层 `16,532,562 → 18,473,202`，**只涨 11.74%**；
  9 层 `18,100,050 → 21,593,202`，**涨 19.30%**。
  因为 embedding 固定占 14,571,952（5 层下占 88.1%），交叉网络翻倍对总量影响有限。

#### 三种"翻倍"必须分清（这是最容易写错的一处）

| 量 | 值 | 性质 |
|---|---|---|
| 单子网 vs 双子网 | **精确 2.000000** | 定义使然（模型里有两个子网） |
| LCA(r=1/2) vs 全秩(r=1)，同口径 | **1.9898**（5 层）/ **1.9901**（9 层） | 非 2，见上 |
| 论文印的 `0.78→1.56` | 2.0000 | **舍入巧合**（0.784→1.561 实际 1.99×） |
| 论文印的 `1.76→3.51` | 1.9943 | 也是 1.99 量级 |

> **不要写"LCA 参数量翻倍等于 2.00×"**。论文那个"2×"是两位小数的舍入巧合，不是精确关系。
> 精确关系只有"单子网 vs 双子网 = 2.000000"这一条。

### 2.5 与论文的关系边界（报告里最容易被质疑的一点，必须写清）

四个压缩率档位**与论文的关系并不相同**，不能一律说成"论文原版的变体"：

| 档位 | 与论文的关系 | 代码路径 | 依据 |
|---|---|---|---|
| **r = 1/2** | **论文 LCA 原版** | LCA（`w:D→D/2` + γ/β + concat） | 与原仓库**逐位一致**（4/4 `torch.equal` 已验）；论文 FCN𝑝 1.76M 对得上 |
| **r = 1** | **论文 `-full` 变体** | **全秩**（`w:D→D`，无 γ/β、无 concat） | 论文四数反解，带 γ/β 会得 1.57/3.52 与论文 1.56/3.51 不符（§2.2b） |
| **r = 1/4、r = 3/4** | **本文自定义扩展**（论文无对应档） | LCA + 零参数宽度适配器 | 见下 |

**为什么 r=1/4、3/4 不是论文原族**：论文的 `concat[H_1, H_2]` 只在 `2d == D`（即 **r=1/2**）时
才能保持输出维度不变——因为 `H_2 = γ⊙H_1 + β` 是逐元素仿射，宽度必然等于 `H_1`。
`r ≠ 1/2` 时拼接宽度 `2rD ≠ D`，**必须引入论文没有的维度恢复操作**，否则残差 `(H + b)` 形状不匹配。

**本文采用的做法**：**零参数**宽度适配器
（`2d < D` 时平铺后截断；`2d > D` 时补零后分组求和）。
它不引入任何可训练参数，因此**参数量仍严格只由 d 决定**（`参数量 = L·(D·d+2d+D) + (D+1)`，
已由解析式与实测逐项对账，见 §2.3）。这一点是"参数量-AUC 曲线"能有干净自变量的前提。

**但必须声明**：

> r=1/4、r=3/4 两个档位的 **AUC 结论属于探索性分析**，
> 不能等同于论文原版的行为，也不能声称"复现了论文的趋势"。
> 它们回答的是本文自己提出的问题：*若把 LCA 的压缩率自由化，参数量与精度的关系如何？*
> 而 r=1/2 与 r=1 两个档位才是可严格对照论文的锚点。

**另需声明结构不连续**：r=1 走全秩路径、r<1 走 LCA 路径，两者**不是同一个网络结构**。
所以四个点**不能当作一条连续曲线上的四个采样**——跨过 r=1 时换的是结构，不是单纯调宽度。

### 3.3 两个"假变异"的教训（值得写进报告）

原本还想测两个变异，实测发现它们**在数值上根本不产生差异**，因此不是变异：

**(a) concat 顺序 `[H1,H2]` → `[H2,H1]`**
初始化时 `γ=1, β=0`，所以 `H_2 = γ⊙H_1 + β ≡ H_1`，两半**就是同一个张量**，交换顺序完全一致。
这本身是 LCA 的一个真实性质：**第一步时"宽度翻倍"并没有带来任何新信息**，
要等训练把 `γ/β` 学偏离 `(1,0)` 之后两半才开始分化。
这个观察对 §4 的预期效应量判断有用——它解释了为什么增大 r 的收益可能有限。

**(b) 残差写法 `a*(H+b)+x` → `x+a*(H+b)`**
IEEE754 浮点加法满足交换律（`a+b` 与 `b+a` **精确相等**，不是近似），所以这不是变异，是同一个计算。

## 4. 预期效应量（必须诚实写的部分）

### 4.1 改动一：大概率测不出

`[论文]` Table 4（Criteo）：w/o Tri-BCE `logloss 0.4367 / AUC 81.55`，完整 FCNsp `0.4357 / 81.63`。
**Tri-BCE 整个组件的总贡献 = 0.08pp = 0.0008 AUC。**

我们只改它内部的一个细节（权重的截断方式），预期效应量 **≤ 0.0005 AUC**，即不超过整个组件的 60%。

按配对设计功率分析（σ=0.001，α=0.05 双侧，power=0.80）：

| 要分辨的效应 Δ | Cohen's d | 公式值 n | 需要配对数 |
|---|---|---|---|
| 0.0005 | 0.50 | 31.40 | **32 对** |
| 0.0008 | 0.80 | 12.26 | 13 对 |
| 0.0010 | 1.00 | 7.85 | 8 对 |

（已用 `code/src/tools_power_analysis.py` 独立复算，三行全部一致。公式 `n=(z_{1-α/2}+z_{1-β})²/d²`。）

**反向看更直观**：本项目可承受的 5~7 对，只能分辨 Δ ≈ **0.0011**（0.11 pp）——
而预期效应量 ≤ 0.0005（0.05 pp）。**确实测不出。**

#### ⚠️ 单位换算：一对 = 2 次训练（这里是本方案最容易算错的地方）

配对设计里 **「一对」= 基线跑一次 + 改进跑一次 = 2 次训练**。
所以「32 对」对应 **64 次训练**，不是 32 次。**漏掉这个 ×2 会把算力需求低估一半。**

| 配对数 | 训练次数 | 76 min/次 | 150 min/次 |
|---|---|---|---|
| 8 | 16 | **20.3 小时** | 40.0 小时 |
| 13 | 26 | **32.9 小时** | 65.0 小时 |
| 32 | 64 | **81 小时** | 160 小时 |

算力结论：**32 对需 81~160 小时（约 3~7 天）**。
下限是 **81 小时**，不是 40.5 —— 40.5 只是 32 次（= 16 对）的量，不要误读成"32 对只要 40 小时"。

⚠️ 单次耗时**随 DCU 负载显著变化**（有第三方进程占满 6 核配额），实测区间 76~150 min/次。
故报告里建议写「81~160 小时（约 3~7 天）」，并注明随负载浮动，不要写单一精确值。

> **方法论备注（本项目真实踩过）**：我曾看到 `76×32=40.5≠81` 就断定原数字错了，
> 于是把对的 81 改成错的 40.5——因为没先确认 **"32" 的单位是"对"还是"次"**。
> **纠正一个不存在的错误比原错误更危险**，因为它披着"我自查过了"的外衣。
> 自查流程应是：**先确认单位定义，再做乘法**，第二步才是比较结果。

**所以我们会写**：在可承受的种子数下（5~7 对），若测不出显著差异，这**不是**改进失败的证据，
而是说效应量低于本实验的可辨识下限。这个结论本身是有价值的——它量化了"这类微小改动在 Criteo 上不可验证"。

### 4.2 改动二：确定性，可严格验证

参数量是**确定性测量，零种子噪声**，n=1 即可严格验证：§2.3 已完整给出，解析式与实测完全吻合，
且与论文 Table 5 的四个数全部对上。

**关于"延迟降 23%"——已核实，且结论是：我们不能宣称这条**（详见
`docs/延迟实测与论文23%矛盾_20261118.md`）：

1. **论文自身数字不一致**（纯文本核算即可确认，不依赖我们的硬件）：
   论文正文三处说"延迟降约 23%"，但其 Table 5 四个可比比值是
   **27.02% / 27.98% / 31.24% / 26.74%**，**没有一个落在 23%±1pp 内**。
   这是论文内部的矛盾，是个硬发现，比我们的实测更有说服力。

2. **我们的实测也测不出 r 对延迟的影响**（captain 在 DCU 上实测）：
   r=0.25/0.50/0.75/1.00 的完整前向分别是 0.0015/0.0015/**0.0031**/0.0014 ms/sample，
   r=0.75 反而最慢、r=1.00 最快——物理上不可能，说明**测量分辨率不够**。
   原因：embedding 占参数 88.1% 但是**查表（gather）不是矩阵乘**，计算量近零且不受 r 影响；
   其访存开销 + DCU 小算子 kernel 启动开销淹没了交叉网络的差异。

**所以 E4-B 的结论重心是「参数量」，不是延迟。** 延迟列只报实测值 + 测量口径，
**不据此宣称 LCA 的延迟收益**。⚠️ 也不能说"论文的 23% 是错的"——
我们测不出 ≠ 它不存在，论文可能用了不同协议（batch=1、含 Python 开销等）。

精度方面，`r` 对 AUC 的影响 `[待测]`。预期：

- r 变小（1/4）→ 参数量降 9.7%（9 层口径），精度可能持平或略降
- r 变大（1）→ 参数量涨 19.3%（9 层口径），精度可能持平或略升

**关键判断（基于 §3.3(a) 的观察）**：`γ=1, β=0` 初始化下两半同值，
意味着 r 增大带来的"额外容量"在训练初期并不生效，需要训练把它用起来。
所以**r 的收益很可能是弱单调甚至不单调的**，这条曲线本身就是有信息量的结果。

### 5.2 为什么 yaml 是纯 ASCII（踩过的坑，附精确触发条件）

fuxictr 2.0.1 的 `load_config()` 用 `open(config, 'r')` **没有指定 encoding**，
于是按 `locale.getpreferredencoding()` 解码。若该 locale 不是 UTF-8，
**yaml 里有任何非 ASCII 字节都会 `UnicodeDecodeError`**，训练还没开始就崩。

`[实测]` 精确触发条件（本机复现）：

| 条件 | 结果 |
|---|---|
| `locale.getpreferredencoding() = cp936`（GBK，本机默认）+ yaml 含中文 | **UnicodeDecodeError: 'gbk' codec can't decode byte 0xad in position 56** |
| `PYTHONUTF8=1` / `-X utf8`（强制 UTF-8 模式） | 读取正常 |
| yaml 纯 ASCII（无论 locale） | 读取正常 |

关键点：**`allow_unicode=True` 会把中文原样写成 UTF-8 字节，因此留下非 ASCII 字节**；
`allow_unicode=False` 会转成 `\uXXXX` 转义，文件保持纯 ASCII。

`[实测]` 远程 DCU 当前是 `LANG=`（空）+ `sys.flags.utf8_mode = 1`（Python 自动启用 UTF-8 模式），
因此**远程此刻不受影响**。但这依赖 LANG 为空这一偶然条件：
只要有人在 `LANG=C`、`LC_ALL=POSIX` 或 Windows GBK 下跑，就会崩。

**因此本项目的策略是：不依赖 locale**——所有 yaml 保持纯 ASCII，中文解释全部写在本文与 Python docstring 里。
`[实测]` 交付扫描：`code/configs/model_config.yaml` 与 `dataset_config.yaml` 非 ASCII 字节数均为 **0**。

## 6. 与原仓库的隔离方式（为什么 A/B 可信）

改进版在 `code/src/`（包名 `src`），原仓库在 `code/FCN/src`（**只读**）。
两者靠 `sys.path` 不同区分，绝不在同一进程里以 `src` 之名共存。

但逐位一致测试需要**在同一个进程里**同时持有两者。做法：`code/src/_orig_loader.py` 用
`importlib.util.spec_from_file_location("fcn_orig", ..., submodule_search_locations=[src_dir])`
把原仓库加载成名为 `fcn_orig` 的独立包。必须给 `submodule_search_locations`，
否则原仓库 `__init__.py` 里的相对导入 `from .ECN import *` 解析不了。

`_orig_loader.py` **只读**原仓库文件，绝不写入。原仓库 `FCNv2.py` 的 sha256 在
`remote_verify_improve.sh` 第 1 节里打印，可用来证明未被改动。
