**断连发生在我的清理命令执行过程中，我必须说明，不掩盖。**

### 我执行了什么
在 02:04 左右，我为清理孤儿进程 22668，执行了：

### 我能否排除自己的责任
**不能完全排除，但我判断可能性低**，理由：
1. 命令精确指向 22668 及其子进程，不涉及 sshd / ssh 会话链
2. 但**连接确实在该命令执行中中断**（报 `Connection closed by 223.113.240.64 port 10188`）
3. 因此**无法排除「该命令触发了某个我没预见到的连锁反应」**

### 另一个更可能的解释
平台实例可能因配置的时长上限 / 资源策略自动关机。支持证据：
- 主机 ping 通（42 ms）但**所有 SSH 端口 refused** —— 这是「实例已关机但网络设备仍在」的典型表现
- 若是我的 kill 误伤 sshd，通常表现为「连接挂起」而非「端口 refused」
- 节点已连续运行 **2 天 17 小时**，可能触及平台时长限制

### 我的结论
**无法确定因果，两条解释都无法排除。** 若节点恢复后 sshd 日志可查（`journalctl -u sshd`），
可以判定；若实例是全新启动，则倾向于「平台关机」。

## 七、这次事故的两条教训

### 1. 多人协作时，长任务的启动权必须唯一
captain 在 01:58:47 启动，我在 01:59:43 也启动（**我不知道他已经启动了**），
两者参数完全相同、输出目录完全相同，造成：
- `seed2026` 的 train.log 被两个进程争抢（产生 `.failed-` 归档）
- 我 kill 自己那个后留下孤儿进程链

**正确做法**：启动长任务前先 `pgrep` 检查，并发消息确认「谁启动了」。
我上面的恢复命令已内置这条。

### 2. 「清理孤儿进程」这个动作本身有风险，应先确认影响面
我执行 `pkill -P 22668` 时，没有先列出它的完整子孙树、没有确认这些进程是否安全可杀。
**更稳的做法**：
```bash
# 先看会杀什么，再执行
pstree -p 22668
ps --ppid 22668 -o pid,cmd
# 确认无误后才 kill
```
**这次虽然命令是精确的，但缺乏「先看后杀」这一步。**
