## 二、参数量公式在真实数据上精确命中

这是最有说服力的验证：

| 项目 | 值 |
|---|---|
| 实测参数量（真实格式数据） | **2,427,922** |
| 闭式公式预测 | **2,427,922** |
| 一致 | **是** |

闭式公式（已写进 `tools/param_formula.py` 的口径）：
```
D = 字段数 × embedding_dim = 39 × 16 = 624
每层 cross 参数 = D×(D/2) + D/2 + D/2 + D = 195,936
单网络 = (exp层数 + lin层数) × 每层参数 + (D+1)
总参数 = Σ(各字段 vocab_size) × embedding_dim + 2 × 单网络
```

**为什么这条重要**：它证明我们对模型结构的理解与代码实现**完全一致**。
后面 runner 每跑完一个实验，都可以用这个公式独立核对参数量，
一旦对不上就说明配置没生效或代码被改坏了。这是一道自动防线。

## 三、顺带确认：I 字段的 bucketize 确实生效

小样本下各字段 vocab_size：`I1=30, I2=74, I3=62`。
真实全量下应该是 `I1=44, I2=99, I3=122`（作者日志值）。

小样本值更小是**正确**的：因为只见到少量取值，而且 `min_categr_count`
会把低频值合并成 OOV。这反过来说明 `convert_to_bucket`（⌊log2(x)⌋）
这个预处理真的执行了，不是被跳过。

## 四、这次验证排掉的三个雷（都是会卡死几小时的）

### 雷 1：`run_expid.py` 用错 FeatureProcessor（已确认必须改）
官方 `run_expid.py` 第 28–29 行：
```python
from fuxictr.preprocess import FeatureProcessor          # 通用版
from fuxictr.datasets.kkbox import FeatureProcessor      # ← 覆盖掉了！
```
KKBox 版没有 `convert_to_bucket`，Criteo 的 I 字段配置要求它有，
于是必然报 `AttributeError: 'FeatureProcessor' object has no attribute 'convert_to_bucket'`。

**已验证的正确写法**：
```python
from fuxictr.datasets.criteo import FeatureProcessor
```

作者自己没踩到，因为他日志里 `data_format: h5`，跳过了 CSV→h5 这一步。

### 雷 2：sklearn 版本边界在 1.5.0（已确认）
`fuxictr/metrics.py:30` 调用 `log_loss(..., eps=1e-7)`。
sklearn 1.5.0 起删除了 `eps` 参数 → `TypeError: got an unexpected keyword argument 'eps'`。

实测：
- sklearn **1.4.2**：`log_loss` 签名含 `eps`，**能用**（会给 FutureWarning，无害）
- sklearn 1.5.0 / 1.5.1 / 1.5.2 / 1.7.2 / 1.9.1：**不能用**

**服务器已装 1.4.2，正确。**

### 雷 3：numpy 2.x 的 `np.Inf`（仅本机）
`fuxictr/pytorch/models/base_model.py` 用了 `np.Inf`，numpy 2.0 已移除。
**服务器 numpy 固定 1.25.0，`np.Inf` 仍在，不受影响**，无需处理。
