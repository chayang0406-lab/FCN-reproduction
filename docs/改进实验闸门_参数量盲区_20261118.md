# 改进实验（E3/E4-A/E4-B）的开跑闸门：为什么参数量不够

> runner，2026-11-18。E0 的闸门已修好（`_v2`），但**改进实验这条链路还有一个更隐蔽的盲区**。
> 本文给出一份可直接执行的体检工具与实测证据。

## 一、问题：15 个配置里有 8 个参数量完全相同

实测 `code/configs/model_config.yaml` 全部 15 个 expid 的参数量：

| n_params | 个数 | expid |
|---|---|---|
| **16,532,562** | **8** | `base`, `soft_smoothmax`, `soft_softplus`, `soft_ratio`, `soft_smoothmax_anneal`, `abl_no_tribce`, `abl_exp0`, `abl_lin0` |
| 15,556,002 | 1 | `r025` |
| 17,509,122 | 1 | `r075` |
| 18,473,202 | 1 | `r100` |
| 16,342,242 | 1 | `9L_r025` |
| 18,100,050 | 1 | `9L_r050` |
| 19,857,858 | 1 | `9L_r075` |
| 21,593,202 | 1 | `9L_r100` |

**参数量闸门对 8/15 个配置完全失效。** 两个具体后果：

### 后果 1：E3（Tri-BCE 软权重）无法被参数量验证

软权重只改 `add_loss` 里权重的算法，**不增减任何参数**。
所以 `FCNv2_C_soft_smoothmax` 与 `base` 参数量都是 16,532,562。

若 `tri_bce_mode` 因拼写错误、或 fuxictr 的 `kwargs` 传递问题没被读进去：
- 参数量照样 16,532,562 → 闸门照样 OK
- 跑 8 个种子 × 76 分钟 ≈ 10 小时
- 得到的其实是**基线重复**，与 E0 做配对检验会得到 Δ≈0，然后被解释成「软权重无效」

**这是最糟的失败模式**：不是报错，而是给出一个看起来合理的错误结论。

### 后果 2：E4-A 消融无法被参数量验证

`abl_exp0`（0 ECN + 5 LCN）与 `abl_lin0`（5 ECN + 0 LCN）与 `base`（4+1）
**层数和都是 5**，所以参数量也全等。

若 `abl_exp0` 配置写错（比如漏改 `lin_num_layers`，写成 4/1）：
- 参数量不变 → 闸门放行
- 「w/o ECN」这个消融跑出来的其实是基线
- 报告会写「去掉 ECN 后 AUC 无变化」——**一个凭空捏造的结论**

## 二、解法：4 维校验

工具：`tools/verify_improved_configs.py`

| 维度 | 能抓到什么 | 抓不到什么 |
|---|---|---|
| A 参数量 | LCA 7 个档位的配置错误 | 8 个同参数量配置之间的错误 |
| B `(exp,lin)` 层数结构 | `base` / `exp0` / `lin0` 混淆 | 软权重配置错误 |
| C `tri_bce_mode` **从模型实例读** | 软权重反向、拼写错误、未生效 | 层数错误 |
| D `lca_compress_ratio` **从模型实例读** | 压缩率未生效、与参数量不自洽 | — |
| E Σvocab == 910,747 | 数据口径不对 | — |

**关键设计**：C/D 读的是**模型对象上的属性**（`model.tri_bce_mode`），
不是配置文件里的值。配置写了但没生效，这一层能抓到。

**基准值不来自实测**：`expected_params()` 按结构算（`D=624`、`emb=910,747×16`、
`r=1` 无 γ/β），所以配置错了不会被写进基准表。

## 五、已生成的闸门基准表

`runs/expected_params.json` 记录了 15 个 expid 的**期望**值（参数量 + 层数 + tri_mode + lca）。

**用途**：任何一次 run 结束后，拿 `result.json` 与之比对，四个维度全等才算配置生效。
这比「只看参数量」严格得多。

**注意**：基准表里 `n_params` 是按结构算的期望值，不是从实测反推的。
所以即使某次实测跑错，基准表不会被污染。

## 六、还没覆盖的两个盲区（如实说明）

1. **`tri_bce_alpha / beta / anneal_lambda / anneal_floor` 的取值是否正确**
   当前只校验 `tri_bce_mode`。若 alpha 写成 0（等价于关掉软权重），参数量与 mode 都不变，
   本工具查不出。**建议**：把关键超参一并写进基准表并比对 `result.json` 的
   `improvements` 字段（`run_improved.py` 已把它们写进 result.json）。

2. **`soft_smoothmax` 与 `soft_smoothmax_anneal` 的差异只在 anneal 参数**
   两者 `tri_bce_mode` 相同，本工具视为同一期望值。若 anneal 没生效，
   两者会跑出完全相同的结果。**建议**：E3 完成后比对两者的 result.json，
   若逐位相同则说明 anneal 未生效，需要查。

这两条都不阻塞开跑，但写报告时若涉及 alpha/anneal 的结论，必须先验证。
