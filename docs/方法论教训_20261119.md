# 方法论教训：三类「不崩溃的错误」

> runner，2026-11-19 02:55。本文整理本项目一晚（2026-11-18 20:40 → 11-19 02:55）中
> 团队（captain / runner / writer / infra / data / modeler）实际出现的错误，
> 按**失效形态**分三类，每条给「现象 / 根因 / 防护措施」。
>
> **为什么这份文档重要**：本项目的技术结论（E0 复现、机制路径、LCA 参数量）都可以重跑，
> 但**「如何发现自己错了」这件事不可重跑**——它只能被记录和传递。
>
> **一句话总结**：本项目所有严重错误都不是崩溃，而是**输出一个看起来合理的结果**。
> 崩溃会被发现，合理的错误会被写进报告。

---

## 分类框架

| 类 | 形态 | 危险度 | 为什么 |
|---|---|---|---|
| **A** | 输出看着对但结果不对 | ★★★★★ | **不告警**，输出齐全、参数量正确、文件已写 |
| **B** | 数字对但对象错 | ★★★★ | 数字本身可验证，但**对应错了对象** |
| **C** | 判断阈值错（误报） | ★★★ | 会告警，但方向反了（把正常判为异常）|

**A 类最危险**，因为它与「一切正常」在表面上无法区分。

# A 类：输出看着对，但结果不对

## A1 `run_e0_baseline.py` 的三个缺陷

### 现象
1. 跑崩的 run 被永久 `[skip]`（因 `train.log` 非空即判完成，而 traceback 也是非空）
2. 参数量 `MISMATCH` 只打印一行后继续跑下一个种子
3. `mean_epoch_seconds` 恒为 `None`

三者共同点：**程序退出码 0、日志正常、summary 已写**。

### 根因
- 判据用了**弱信号**（「文件非空」）代替**语义判据**（「三项指标齐备」）
- 「警告」被当作「闸门」—— 打印但不阻断
- 时间差分用了 `Epoch=N start` 行，而 fuxictr **只在第一个 epoch 打一次 start**

### 防护措施
| 措施 | 实现 |
|---|---|
| 判据改为语义判据 | `is_run_complete()` = valid AUC + test AUC + 参数量正确，三项齐备 |
| 警告升级为闸门 | `MISMATCH` → `sys.exit(2)`，剩余种子不跑 |
| 计时改用 end 差分 | `epoch_1 = end_1 - start_1; epoch_N = end_N - end_{N-1}` |
| **解析失败自证** | 输出 `n_epoch_start_lines` / `n_epoch_end_lines`，用「行数为 0」自证失效 |

**最关键的一条**：最后一项。前三条防的是「已知的失效」，最后一条防的是
「**解析器静默失效**」——因为解析失败会返回空列表而不是抛异常。

## A2 `--seeds 2025,2026` 只跑了第一个

### 现象
`run_e4b.py` 传 `--seeds 2025,2026,2027`：
- 4 档全部跑完
- 参数量全部正确
- `e4b_results.json` 已写出
- **但只跑了 2025，2026/2027 被静默丢弃**

输出里没有任何异常。

### 根因
```python
"--seed", str(args.seeds[0])   # 硬取第一个
```
`stage_full` 对每个 r 只调一次 `run_one`，所以列表长度被完全忽略。

### 防护措施
```python
# 修前：run_one(args, expid, out, log)          # 内部偷偷用 seeds[0]
# 修后：run_one(args, expid, out, log, seed=seed)  # seed 必传
```
**「把可选改成必传」是结构性修复**——让「忽略来源」在类型层面不可能。

**同思路的另外两处**：
- `author_baseline.author_epoch_auc(epoch)` **必须返回行号**，调用方无法忽略来源
- `e0_startup_check` 的 `is_run_complete` 不接受「参数缺失」为合法输入

**附带修的第二半**：目录结构 `runs/e4b_9L_rXXX/` → `runs/e4b_9L_rXXX/seedN/`。
原来没有 seed 层，多 seed 会**互相覆盖**。
> 很多人只修前半（遍历 seed），不修后半（目录冲突），结果覆盖后依然只剩一个。

## A3 `valid=None` 打印成 `-1.000000`

### 现象
```python
print("valid=%.6f" % (r["final_valid_auc"] or -1))
```
当解析不到 valid AUC 时，输出 `valid=-1.000000`。
**这看起来像一个真实的数值**，读者不会意识到它是占位符。

### 根因
`None or -1` 把「缺失」转换成了一个**在值域内**的数。
`-1` 在 AUC 的合法范围之外，但**在格式化输出里与真值无法区分**。

### 防护措施
```python
("%.6f" % r["final_valid_auc"]) if r["final_valid_auc"] is not None else "None"
```
**原则：缺失值必须以「不可与数值混淆的形态」输出。**

同类的另外两处（都在本项目出现过）：
- 「作者 ep20 = 0.815587」：**这一行根本不存在**（作者只有 19 轮），但被配了一个真实数值
- 「`pgrep` 不存在 → 有进程在跑」：命令缺失被当成命令有输出

## A4 `pgrep` 不存在时误报「有进程在跑」

### 现象
Windows 上跑 `recover_after_outage.py`：
```
subprocess.run("pgrep -af ...", shell=True)
→ stderr: "'pgrep' is not recognized as an internal or external command"
→ out 非空 → 被判定为「有进程在跑」
```

### 根因
**「非空」被当成「有内容」**。stderr 的错误信息也是非空输出。

### 防护措施
```python
def sh(cmd):
    ...
    missing = ("not recognized" in low or "not found" in low or "不是内部或外部命令" in out)
    return rc, out, missing      # 三返回值，调用方必须处理 missing
```
**原则：区分「命令不存在」与「命令有输出」。**

## A5 「解压中读到 2^31-1」差点误判数据损坏

### 现象
`unzip` 正在写 `train.csv` 时读文件大小，得到 `2,147,483,647`（= 2³¹−1）。
`valid.csv` 行数从 4,584,063 变成 2,629,585。
**看起来像数据损坏。**

### 根因
读到了**写入中的中间状态**。`2^31-1` 是 32 位偏移上限的典型信号。

### 防护措施
验收前必须先确认**没有写入进程**：
```bash
pgrep -af unzip | grep -v pgrep || echo "解压已完成 ✅"
```
**若误判为损坏，代价是重新上传 4 GB（约 65 分钟）。**

## A6 `e0_guard --summarize` 把无效 run 算进统计

### 现象
它**自己打印**「这些 run 的结果作废」，但**仍把它们的数值算进 mean/sd**。

### 量化后果
| | valid mean | sd | 分辨 0.001 需配对 | δ_min |
|---|---|---|---|---|
| 含无效 run | 0.508137 | 0.007253 | **826** | 0.016592 |
| 剔除后 | 0.512206 | 0.002430 | **47** | 0.005559 |

**功率分析被放大 17.6 倍，δ_min 放大 3 倍。**
若报告采用错误的 δ_min，会把「可分辨的效应」判成「不可分辨」——**结论方向反了**。

### 根因
`va = [r["valid_auc"] for r in rows if r["valid_auc"]]` —— 「有值」不等于「有效」。

### 防护措施
```python
usable = [r for r in rows if r["param_ok"] and r["has_result"]]
va = [r["valid_auc"] for r in usable]
```
**并且**：`e0_final_summary.json` 新增 `n_valid` / `n_excluded` / `excluded_runs[]`，
让「排除了什么」也进入产物。

# B 类：数字对，但对象错

> 这一类比 A 类更隐蔽，因为**数字本身可验证**。
> 你检查它「是不是算对了」，会得到「对」；但没人检查「它是不是在说那件事」。

## B1 `r=1 比论文少 11,232`

### 现象
我说：「r=1.0 参数量比线性外推少 11,232，是 full_rank 无 γ/β 的设计」。

### 事实
**论文 Table 5 的 3,510,625 与我们实测完全一致，差值 0。**

### 根因
我把「**r=0.75 → r=1 的增量**」与「**r=1 相对论文的值**」混为一谈。
- 「增量少 11,232」这个数字本身是**算对的**（r=1 走 full_rank，每层少 2×proj）
- 但我把它**解释成「比论文少」**，而论文的值就是 full_rank 路径的结果

### 防护措施
**所有「与论文对比」必须先跑「公式 vs 论文 Table 5」的自证**（4 个数差值必须为 0）。
`run_e4b.py` 的 `report` 阶段把这一步放在**最前面**，不通过就 `return 2` 并声明「表不能用」。

## B2 E4-B 用了 5 层的参数量当 9 层

### 现象
我写「交叉网络 980,305 → 1,950,625 = 1.99×」。
这两个数是 **5 层**（E0 口径），而 E4-B 是 **9 层**（论文 FCN𝑝 口径）。

### 为什么难发现
- 两个数都能自算出来
- 比值也确实是 1.99×
- **唯一的问题是层数错了**

### 后果
若用 5 层数，会得出「参数只有论文一半（980,305 vs 1,764,049）」的错误结论。

### 防护措施
**期望值按结构算，不从实测反推**；并且**同时打印层数**：
```
[表 1] 参数量（9 层，E4-B 主结论）
  r     proj  交叉/每子网  交叉/两子网  模型总参数
  0.50  312   1,764,049   3,528,098  18,100,050
```
**表头写明层数**，读表的人能立刻发现对象错。

## B3 embedding 占比 88.1% 被用到 9 层配置

### 现象
captain 在延迟讨论里写「embedding 占参数 88.1%，所以交叉网络变化被淹没」。
实算：
```
5 层 r=0.5（E0，16,532,562）：EMB 占 88.14%   ← 88.1% 只对这个成立
9 层 r=0.5（E4-B，18,100,050）：80.51%
9 层 r=1  （21,593,202）：       67.48%       ← 交叉网络占 32.5%
```

### 后果
**「交叉网络变化被淹没」这个论证在 r=1 端变弱了**（交叉网络从 11.9% 升到 32.5%，2.7 倍）。

### 防护措施（captain 采纳的写法）
> 因 embedding 查表在各档均占参数 67.5%–80.5%，且其计算量近零，交叉网络宽度变化
> 对端到端延迟的影响低于本测量分辨率。需要说明的是，随 r 增大，交叉网络参数占比由
> 19.5%（r=1/2）升至 32.5%（r=1），「被淹没」这一机制在 r=1 端相对减弱。
> 但**实测显示延迟在各档仍未呈现可分辨的单调变化**（r=0.75 反而最高、r=1 最低），
> 说明主导因素仍是测量分辨率而非参数占比。

**关键手法：用实测观测补强理论，而不是用理论掩盖观测。**

## B4 「191.2 s/epoch」被当成 E0 的耗时

### 现象
多个文档混用「作者 191 秒/epoch」作为 E0 的对照。

### 事实
| 日志 | 实现 | 参数量 | 轮数 | s/epoch |
|---|---|---|---|---|
| `FCNv2_Criteo.log` | **旧实现** 3ECN+3LCN | 16,138,194 | 20 | 191.22 |
| `_016_cde6d2ff.log` | **HEAD** 4+1 | 16,532,562 | 19 | **204.38** |

**191.2 属于旧实现，不可复现。E0 的基准是 204.38。**

### 防护措施
**把基准写进代码常量**（`tools/author_baseline.py`），并要求所有工具：
1. 从常量取数（不硬编码）
2. **输出基准日志文件名**（用错时一眼可见）
3. **显式列出「不要用作基准的日志及原因」**

```python
AUTHOR_BASELINE = {"log": "FCNv2_Criteo_016_cde6d2ff.log", ...}
NOT_A_BASELINE = {"FCNv2_Criteo.log": {"why": "旧实现 3ECN+3LCN，复现不出..."}}
```

**并且常量本身也要被验证**：用独立解析真实日志的路径去核常量（8 项全等才通过）。

## B5 作者逐轮值被「补」出来（三人各犯一次，40 分钟内）

### 现象
- writer 写了作者 ep18 = 0.812278（编的）
- captain 写了作者 ep20 = 0.815587（实际是 ep16 的值）
- runner 用下标配对时越界，把「我们的 ep20」配了一个不存在的作者值

### 根因
**「作者逐轮值」是高危数据源**，因为：
1. 它分散在 19 行日志里，需要逐行抽
2. 前几轮核对过之后，后面的就容易「凭记忆补」
3. **位数相似**（0.815xxx），错了也看不出来

### 防护措施
1. **一律从日志现抽，不凭记忆**（`sed -n 'Np'` 或正则）
2. **逐轮值必须带行号**：`_016 line 198: AUC 0.815627 (ep17)`
3. **超过 19 的轮次必须写「作者已早停，无对应」**，不留空、不写 `—`
   （`—` 可能被读成「未测」，而「作者已早停」是事实陈述）
4. **格式敏感性**：逐轮是 `AUC: X - logloss: Y`，最终评估段是 `logloss: X - AUC: Y`（**顺序相反**）
   —— 这个差异可用来区分，但要显式利用

# C 类：判断阈值错（误报）

## C1 `n_epochs <= 1` 被判为 FAIL

### 现象
`e0_startup_check.py` 第一版在 E0 刚跑完第 1 轮时输出：
```
[FAIL] n_epochs = 1 ≤ 1
       第一个 epoch 可能还没跑完，或 P4 复现了
EXIT=1
```

### 根因
我把「刚跑完第 1 轮」这个**完全正常的状态**当成异常。
真正的 P4 特征是 `end_lines == 0` 或 `mean == None`，**不是 `n_epochs == 1`**。

### 后果（如果没被真实数据打脸）
这个工具会在**每次开跑 5 分钟时误报 FAIL**，然后所有人学会忽略它的 FAIL 列表
—— **正中「总在报警的警报器等于没有」**。

### 防护措施
```python
if probe["n_epoch_end_lines"] == 0:        # 真的失效
    fails.append(...)
elif probe["mean_epoch_seconds"] is None:  # 真的失效
    fails.append(...)
else:
    if probe["n_epochs"] == 1:
        print("  [info] 当前只完成 1 轮 —— 正常（E0 才刚开始）")
```

**并且必须做负向回归**：改判据后，P4 场景（只有 start 无 end）仍须 `EXIT=1`。实测通过。

## C2 「作者日志用 `^` 锚行首能工作，我们的不能」

### 现象
同一个正则 `^(\d{4}-...)` ：
- 在**作者日志**上正常（`end=18`）
- 在**我们的日志**上静默返回空（`end=0`）

### 根因
我们把 **stderr 并进了 train.log**（否则 traceback 会丢），而 **tqdm 进度条写 stderr 且不换行**：
```
100%|█████| 1/1 [00:18<00:00]2025-05-13 06:38:23,835 ... Epoch=1 end
                              ↑ 时间戳不在行首
```

### 这是本项目最有价值的一条教训
> **验证解析器必须用它将来要解析的真实数据，不能用手边的替代数据。**

**三个人（captain / runner / infra）都在这上面翻车，而且都以为修好了**——
因为在作者日志上验证是**通过**的。

### 防护措施
1. 正则**不锚行首**（`re.search` 而非 `re.match`；去掉 `^`）
2. **交叉验证**：拿同一份**我们自己的**日志跑遍所有 parse 实现，比对结果
   （`e0_startup_check.py` 第 5 项，实测抓到 3 处）
3. 该坑的变体：`re.match` 比 `^` **更隐蔽**（锚定隐含在函数语义里，代码审查更容易放过）

**实测抓到的 3 处**：
| 文件 | 症状 |
|---|---|
| `run_e0_baseline.py` | `^` 锚行首 + 用 start 差分（双 bug） |
| `smoke_real_on_dcu.py` | `^` 锚行首 |
| `split_train_eval_time.py` | **`re.match`**（更隐蔽） |

# 跨类的结构性教训

## 教训 1：同一逻辑散布多份 → 必须让不一致自动暴露

同一个「从日志解析 epoch 耗时」的逻辑被抄到 **8 个文件**里。
三个人在「一处改对、另一处没同步」上各翻车一次。

**没有重构（时间不允许），但加了自动检测**：
`e0_startup_check.py` 第 5 项拿真实日志跑遍所有实现，比对 `(n_epochs, mean_epoch_seconds)`，
不一致即 FAIL。

**注意**：这个检测器自己也出过假阳性（把返回 list 的实现误判为「解析不出」），
已修。**验证器本身也需要被验证。**

---

## 教训 2：每个验证器必须有「来自真实失败历史」的负向测试

| 验证器 | 负向用例 | 来源 |
|---|---|---|
| `run_e0_baseline_v2` 闸门 | Σvocab=2359 → MISMATCH | 真实子集测试 |
| `verify_improved_configs` | `abl_exp0` 改 4/1、`tri_mode` 改回 hard | 真实盲区 |
| `e0_guard` 污染修复 | **当初暴露污染的那个用例** | 原始失败用例 |
| `e0_startup_check` | 5 个（未启动 / P4 / 参数量 / traceback / seed 不符）| 真实踩过的坑 |
| `verify_e4a_results` | 参数量对但层数 4/1≠5/0 | 真实盲区 |
| 交叉验证 | `run_e0_baseline` + `split_train_eval_time` | 真实缺陷 |

**共同点：负向用例都来自「已经真实发生过」的失败，不是想象的失败。**

> **正例证明它能跑，负例证明它能拦。只有正例的验证器是安慰剂。**

---

## 教训 3：中间量与结论量必须分开

| 中间量 | 结论量 | 差在哪 |
|---|---|---|
| `epochs_end_lines = 18` | **`epochs_trained = 19`** | 早停轮只打 `early stop`，不打 `end` |
| `σ`（独立种子波动）| **`σ_Δ`**（配对差值波动）| 配对生效时 σ_Δ 远小于 σ |
| 最后一轮 `Metrics` | **`Validation evaluation` 段** | 前者是逐轮值，后者是 best model 的评估（差 5e-4）|
| 参数总量 | **交叉网络参数** | embedding 占 67–89%，总量被稀释 |
| `n_seeds = len(summary)` | **有效 run 数** | 无效 run 不该进统计 |

**报告写「18 轮」会与日志里的 `Epoch==19 early stop` 直接矛盾。**

---

## 教训 4：长任务启动权唯一 + 启动前 pgrep

### 事故
2026-11-19 01:58:47 captain 启动 8 种子 driver（PID 22530），
01:59:43 runner 也启动（PID 22666）——**间隔 56 秒，参数与输出目录完全相同**。

后果：`seed2026` 的日志被两个进程争抢，产生 `.failed-` 归档。

### 双向防护（缺一不可）
1. **启动方**（captain）：启动后 **30 秒内广播**「已启动 + PID + 预期时长」
2. **执行方**（任何人）：启动前**必须** `pgrep` 确认无重复

```bash
pgrep -af "run_e0_baseline_v2" | grep -v pgrep && echo "!!! 已有进程在跑" && exit 1
```

**只写一条不够**：下次可能是别人启动、我来检查。

## 教训 5：清理进程前先「看」再「杀」

### 事故
我为清理孤儿进程 22668，直接执行 `pkill -TERM -P 22668`。
**没有先 `pstree -p 22668` 看会杀哪些进程。**

### 正确做法
```bash
pstree -p 22668              # 先看子孙树
ps --ppid 22668 -o pid,cmd   # 再列具体命令
# 确认无误后才 kill
```

（注：当晚节点失联的因果未定，但**「先看后杀」这个习惯应当无条件建立**。）

# 附：本项目的验证体系（四层）

| 层 | 谁 | 方法 | 为什么需要 |
|---|---|---|---|
| 1 | data | 硬编码期望表 | 快速自检 |
| 2 | writer | 独立脚本 + 查 oov/padding | 不同实现 |
| 3 | **runner** | **从作者日志原文重新抽取**（绕开期望表）| **避免自证循环** |
| 4 | captain | 直接读 json 自己算 | 第四方 |

**四层、四种实现、不同信息源，全部一致。**

**为什么需要四层**：每一层的失败模式不同（硬编码表错、正则错、路径错、读法错）。
**单一验证无论多仔细，都无法排除「验证方法本身有系统偏差」。**

# 结语

本项目一晚出现的所有严重错误，**没有一个是崩溃**。
它们全都是：程序正常退出、日志正常、输出齐全，**只是结果是错的**。

因此本项目的核心方法不是「写更多代码」，而是：

1. **让缺失无法伪装成数值**（`None` 就打印 `None`，不打印 `-1`）
2. **让忽略来源在类型层面不可能**（seed 必传、行号必返回）
3. **让不一致自动暴露**（交叉验证、公式自证在前）
4. **让每个验证器都有来自真实失败的负向测试**
5. **中间量与结论量分开报**（轮数 vs end 行数、σ vs σ_Δ）

**这五条比任何一个实验数字都更难被推翻。**
