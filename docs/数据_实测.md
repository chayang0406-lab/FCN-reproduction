## 二、为什么必须走 hf-mirror.com

`huggingface.co` 从本机直连超时，`hf-mirror.com` 可通。实测该镜像返回 **302 重定向**到
`cas-bridge.xethub.hf.co`（带签名参数的临时地址），因此**必须带 `-L` 跟随重定向**，
且 curl 需要 `--retry` 兜底——签名地址有效期 1 小时，下载中途若断开，重试要重新取签名。

实测下载命令（可直接复用）：

```powershell
curl.exe -L -C - --retry 5 --retry-delay 3 --retry-all-errors --max-time 10800 `
  -A "Mozilla/5.0" --progress-bar `
  -o "D:\中南大学\数据挖掘\data\Criteo_x4.zip" `
  "https://hf-mirror.com/datasets/reczoo/Criteo_x4/resolve/main/Criteo_x4.zip"
```

`-C -` 是断点续传；`--retry-all-errors` 不可省（镜像偶发 429/连接重置）。

**实测坑**：调 `https://hf-mirror.com/api/datasets/reczoo/Criteo_x4` 拿文件清单会返回
**429 Too Many Requests**，别指望用 API 探测，直接用 resolve 直链。

## 四、上传：为什么是 1 MB/s，以及试过哪些更快的办法

这一节记录**失败的加速尝试**，避免后人重复踩坑。

### 4.1 实测各方案带宽

| 方案 | 实测带宽 | 结论 |
|---|---|---|
| `scp` 单流 | **0.66 MB/s** | 最慢 |
| `Get-Content -AsByteStream \| ssh "cat >"` | 约 0.9–1.04 MB/s | 中等 |
| `cmd /c type file \| ssh "cat >"` | **1.05 MB/s** | 与上者同量级，**本文采用** |
| 4 路并行（每路 16 MB 分片） | **合计 1.01 MB/s** | ❌ **并行无增益** |
| `ssh -C`（压缩） | 对全零数据 6.76 MB/s | 见 4.2 |

### 4.2 三个被证伪的加速假设

1. **「并行多流能提升总带宽」→ 证伪。**
   4 路并行实测合计 1.01 MB/s，与单流 1.05 MB/s 完全一样。
   说明瓶颈是**这条链路的总带宽上限**（约 1 MB/s），不是单流限速。
   **别再试 8 路、16 路并行，纯浪费。**

2. **「换加密算法能加速」→ 证伪。**
   `aes128-ctr` 1.04 MB/s、`aes128-gcm@openssh.com` 1.07 MB/s，与默认值无差别。
   说明瓶颈不在 CPU 加密，而在网络。

3. **「`ssh -C` 压缩能加速」→ 条件成立，但本题用不上。**
   全零数据 6.76 MB/s（vs 不压缩 0.84 MB/s），压缩确实能突破带宽墙。
   **但是**：Criteo 的 zip 已经是 DEFLATE 压缩过（36.3%），
   **再压一次榨不出油水**，所以对 zip 用 `-C` 无效。
   → 如果将来要传**未压缩的 CSV**，`ssh -C` 值得一试。

4. **「先用 bz2/lzma 重压缩再传，省时间」→ 算过，不划算。**
   在真实 `train.csv` 的 256 MB 样本上实测三种编码（`tools/bench_recompress.py`）：

   | 编码 | 压缩后比例 | 压缩耗时（单核） |
   |---|---|---|
   | zlib-9（≈ zip 用的那一类） | 36.17% | 11.8 s |
   | bz2-9 | 26.28% | 20.1 s |
   | lzma preset 6 | 17.20% | 232 s |
   | lzma preset 9\|EXTREME | **14.86%** | 364 s |

   外推到 10.38 GB 未压缩 CSV（带宽按 1 MB/s 计）：

   | 方案 | 压缩耗时 | 传输耗时 | **总耗时** |
   |---|---|---|---|
   | 直接传 zip（现状） | 0 | 64 min | **64 min** |
   | bz2 重压 | 14 min | 47 min | **60 min** |
   | lzma-extreme 重压 | 252 min | 26 min | **278 min** |

   **结论：bz2 只省 4 分钟（抵不过风险与重跑成本），lzma 慢 3.3 倍。**
   → 保持「直接传原 zip」。这条留在这里是为了**避免后人再花时间重算一遍**。
   注意：本机 8 物理核，若多核并行 bz2 会更快，但上传期间 CPU 争抢会让
   PowerShell/ssh 管道本身变慢，净收益仍然不成立。

### 4.3 最终采用：分块 + 断点续传

大文件单次管道最大的风险是**跑到 90% 断了要重来**。所以写成
`tools/upload_criteo.ps1`，做法：

- 按 **128 MB** 切 31 块，逐块上传；
- 每块上传后**立刻在远程算 md5 与本地比对**，不一致就停；
- 已完成块写进 `data/.upload_state.json`，**中断后重跑自动跳过**；
- 全部传完后在远程 `cat` 拼回 `Criteo_x4.zip`，**再整体校验一次 zip 的 md5**。

### 4.4 这个设计**实际救了一次**，不是过度设计

本次上传中断 **3 次**，每次都靠续传保住了已传数据：

| 时刻 | 原因 | 损失 | 恢复方式 |
|---|---|---|---|
| 21:07 | `Math::Min` Int32 溢出（见下） | 0（首块前就挂） | 修 bug 重跑 |
| 21:11 | 主动停止，做 4.1/4.2 带宽 A/B 测试 | 0（已传块保留） | resume |
| **22:02** | **`Connection closed by 223.113.240.64 port 10188`**（对端断开） | **0** | **resume，17 块全部命中** |

22:02 那次是关键：已经传了 **2,281,701,376 字节（56%）**，单次管道方案会**全部重来 56 分钟**。
续传直接从 c0017 接着传，日志显示
`resuming, already done: c0012,c0006,...,c0015`（17 块全部找回）。

最终：`DONE uploaded=4,049,391,068/4,049,391,068 elapsed=37min`，
远程拼回后 md5 `41ca8e3ef1fa1dadf95132f5e11570e1` 与本地一致。

> **📌 给后人的结论：跨公网上传 GB 级文件，一定要能续传。**
> 这条链路的断线不是假设，是 86 分钟内实际发生了 1 次。
> 远距离/弱网下把块设小一点（如 64 MB）能进一步降低单块重传成本。

> **PowerShell 坑（已修）**：`[Math]::Min($chunkBytes, $srcLen - $offset)` 在
> `$srcLen` 是 int64 且超过 2^31 时会报
> `无法将参数"val2"转换为类型"4049391068"…for "System.Int32"`。
> 原因是 PowerShell 选中了 `Math::Min(int,int)` 重载。
> 解决：两边都显式转 `[double]` 再取 Min，结果再转回 `[int64]`。

### 4.5 一个诊断陷阱：续传后日志里的 ETA 是假的

断点续传重跑时，`uploadedBytes` 会把"已完成的块"瞬间计入，
导致 `avg` 速率虚高、`eta` 虚假地乐观：

```
[22:05:36] OK c0017 ... pct=59.66% avg=14.06MB/s eta=2min   ← 假象
[22:08:16] OK c0018 ... pct=62.98% avg=7.52MB/s  eta=3min   ← 假象
[22:11:33] OK c0019 ... pct=66.29% avg=4.92MB/s  eta=4min   ← 假象
```
真实速率始终是 **0.5–1.05 MB/s**。**判读进度时看单块速率（第 2 列），不要看 avg/eta。**

> **PowerShell 坑（已修）**：`[Math]::Min($chunkBytes, $srcLen - $offset)` 在
> `$srcLen` 是 int64 且超过 2^31 时会报
> `无法将参数"val2"转换为类型"4049391068"…for "System.Int32"`。
> 原因是 PowerShell 选中了 `Math::Min(int,int)` 重载。
> 解决：两边都显式转 `[double]` 再取 Min，结果再转回 `[int64]`。

## 六、校验方法（行数硬断言 + md5 参考断言）

### 6.1 为什么行数和 md5 不等价

官方 README 给的 md5 是 reczoo 用 **sklearn 0.19.1** 切分、pandas 默认 `to_csv` 写出的产物。
如果解压工具、换行归一化（CRLF→LF）、或 pandas 版本不同，**文件内容语义相同但字节不同**，md5 必然对不上。

所以判定顺序设计为「先硬后软」：

1. **行数**（硬断言）：三份之和必须等于 **45,840,617**，单份分别为 36,672,493 / 4,584,062 / 4,584,062。
2. **列数**（硬断言）：每行必须 **40 列** = 1 个 `Label` + 13 个 I 字段 + 26 个 C 字段。
3. **坏行数**（硬断言）：解析后列数不等于 40 的行数必须为 **0**。
4. **md5**（参考断言）：对得上最好；对不上但 1–3 全过，判定数据可用，但须写明差异原因。

> **本次实测结果**：第 4 条也全部命中（见 7.2），所以这条"退路"没有启用。
> 保留这段设计说明是因为**换数据集（如 Avazu）时仍会需要它**。

### 6.2 校验脚本

`tools/verify_criteo_csv.py`（已随本任务交付，并已上传到远程 `<P>/tools/`）。它**一次流式扫描**
同时得到行数、列数、坏行数、CRLF 标记，不需要把 8.9 GB 的 train.csv 读进内存。

```bash
cd <P>/data/csv
python3 <P>/tools/verify_criteo_csv.py --dir . --json <P>/data/verify_csv_result.json --skip-md5
```

退出码：`0` = PASS，`1` = FAIL。

> **本次实际没有用这个脚本做最终判定，原因要写清楚（这是有意的取舍）**：
> 校验当时 `build_h5.py` 正在同一台机器上做全量转换（占 6 核中的大部分）。
> 而 `verify_criteo_csv.py` 要用 Python 逐行解析 11 GB 文本，比 `wc -l` 慢一个量级，
> 会与转换争抢 CPU 并拖慢关键路径。
> **已有的证据更强且成本更低**：`wc -l`（行数）+ `md5sum`（字节级）+ `unzip -t`（压缩无损）
> 三者合起来已经覆盖了脚本能证明的全部内容。
> 所以**脚本保留为工具**（换数据集时可直接复用），但本次判定依据是 7.1/7.2 的五重证据。
>
> **这是一个可复用的原则**：校验手段要和"证据强度 × 机器成本"一起权衡，
> 不是"多跑一个脚本就更严谨"。在关键路径上跑重复校验是负收益。

### 7.3 ⚠️ 一个差点误判的坑：解压完成的判定

解压 8.9 GB 的 `train.csv` 需要几分钟。中途 `ls -l` 读到 **6,069,616,640 字节**，
**当时误判为「文件截断 / zip 损坏」**，若据此下结论会触发一次 64 分钟的无谓重传。
几百秒后它自然长到了 8,917,742,608。

**正确判据（两个都可靠，推荐第 1 个）**：

```bash
# 判据 1（最快）：unzip 会把成员恢复成 zip 内的原始时间戳
ls -l train.csv | awk '{print $6,$7,$8}'   # 解压完应显示 "Nov 18 2021"
                                            # 解压中显示当前年份 2026

# 判据 2（最稳）：看进程，不要看文件大小
pgrep -af unzip | grep -v pgrep | grep -v "unzip -t" || echo "解压完成"

# 判据 3（若只能看大小）：连续两次采样间隔 ≥2 分钟且数值不变
```

**不要只看 `ls -l` 的大小就下结论。**

### 9.1 为什么这张表是「数据管道正确」的最硬证据

39 个字段**同时**命中，需要三个设置**同时**正确，任何一个错都会让若干字段偏离：

| 设置 | 若设错会怎样 |
|---|---|
| `min_categr_count=10` | C 字段 vocab 会全部偏移（过滤阈值变了） |
| `fill_na=0` / `na_value=0` | I 字段空值处理错 → I1 偏离 44（空值率 44.31%，影响极大） |
| `convert_to_bucket=⌊(ln x)²⌋` | 若用论文正文的 `⌊log2 x⌋`，I1 会从 44 掉到 **11–19** |

**且它不依赖任何随机种子**——不像 AUC 那样受初始化影响，因此可用作编译期级别的断言。

### 9.2 早期验证：抽样 200 万行就能预判规则对错

`tools/predict_bucket_vocab.py` 对真实 CSV 抽样应用两种 bucketize 规则，
**几分钟即可判断规则是否用错**，不必等 3 小时的全量转换：

| 字段 | `⌊(ln x)²⌋` 原始桶数 | `⌊log2 x⌋` 桶数 | 作者全量 vocab |
|---|---|---|---|
| I1 | **47** | 11 | **44** |
| I2 | **99** | 15 | **99** |
| I5 | **219** | 22 | **220** |
| I7 | **80** | 14 | **80** |
| I12 | **37** | 10 | **37** |

> 抽样下 `⌊(ln x)²⌋` 的**原始**桶数 ≥ 全量**过滤后**度数（低频值尚未被过滤），
> 所以 47 vs 44 是正常的；而 log2 是 11 vs 44，**差 4 倍，不可能**。

**这条经验可复用**：任何「全量转换耗时长 + 结果有确定性断言」的任务，

### 10.1 Preprocess 为什么花了 39 分钟：`convert_to_bucket` 是逐元素 `.map()`

源码（`fuxictr/datasets/criteo.py:23-30`）：

```python
def _convert_to_bucket(value):
    if value > 2:
        value = int(np.floor(np.log(value) ** 2))
    ...
return df[col_name].map(_convert_to_bucket).astype(int)   # ← 逐元素 Python 调用
```

实测单位成本：

| 操作 | 单行成本 | 外推 3670 万行 |
|---|---|---|
| **`convert_to_bucket`（13 个 I 字段）** | **3.63 µs/row** | **约 29 分钟** |
| `astype(str)`（26 个 C 字段） | 0.032 µs/row | 0.5 分钟 |
| `isnull().values.any()`（40 列） | 0.064 µs/row | 1.6 分钟 |

**即 preprocess 阶段 99% 的时间花在 `convert_to_bucket` 上**，共约
**3670 万 × 13 = 4.77 亿次 Python 函数调用**。

> **工程观察（可写进报告）**：若改为向量化
> （`np.floor(np.log(arr) ** 2)`），预计快 20–50 倍。
> **但我们保持原实现不改**——改了就不再是作者的预处理口径，复现性会失效。
> 这是一个「性能 vs 可复现性」的取舍，选择可复现性。
