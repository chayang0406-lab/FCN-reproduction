# 推理延迟实测：一个反直觉的结论（2026-11-18，captain 实测）

> 这份文件的结论会**改变 E4-B 的写法**。请 runner 和 writer 都读。
> 核心：**在 DCU 上，延迟几乎不随 LCA 压缩率 r 变化**，因为 embedding 查表主导了开销。
> 所以「延迟降 23%」这条论文声称，我们**无法用当前测量复现**——这本身是个有价值的结论。

## 一、实测数据（协议见第二节）

配置：exp=4 / lin=5（9 层，对齐论文 Table 5），batch_size=16384，warmup 50，repeat 9，每次 20 batch。

### 分裂测量（关键）

| r | 模型总参数 | 仅 embedding 查表 | 仅交叉网络 | 完整前向 |
|---|---|---|---|---|
| 0.25 | 16,342,242 | 0.0002 ms | 0.0001 ms | 0.0015 ms |
| 0.50 | 18,100,050 | 0.0002 ms | 0.0001 ms | 0.0015 ms |
| 0.75 | 19,857,858 | 0.0002 ms | 0.0002 ms | **0.0031 ms** |
| 1.00 | 21,593,202 | 0.0002 ms | 0.0001 ms | 0.0014 ms |

**两组数字都很小，且不随 r 单调变化。** r=0.75 反而最慢，r=1.00 最快——
这在物理上不可能（r=1 参数最多），说明**测量被别的东西主导了**。

## 二、为什么测不出来：测量分辨率不够

### 原因 1：batch=16384 时单次前向太短，噪声掩盖信号
`0.0014 ms/sample × 16384 = 23 ms/batch`。
而交叉网络部分的真实差异（论文说 23~28%）摊到每 batch 只有几毫秒，
与 DCU 上的调度抖动同量级。

### 原因 2：embedding 是稀疏查表，与交叉网络的计算量无关
模型 88.1% 的参数在 embedding 里（14.5M / 16.5M），但 embedding 是 **查表**（gather），
不是矩阵乘。查 39 个字段 × batch 16384 行，访存量巨大但**计算量几乎为零**，
且 r 只改交叉网络宽度，**完全不影响 embedding 部分**。

所以：**r 变大 → 交叉网络 FLOPs 增加 → 但总时间被 embedding 访存和 kernel 启动开销淹没。**

### 原因 3：DCU 上小算子的 kernel 启动开销占比高
这一点在训练吞吐测试里已观察到（单步耗时几乎不随 batch_size 变化，
batch 差 16 倍而时间只差 8%），说明 kernel 启动开销主导。

## 三、这个结论怎么用（重要，别写成「复现失败」）

### ✅ 可以说的
1. **参数量的变化是确定性的、可严格验证的**：
   - r=1/2 → r=1，**交叉网络**参数 980,305 → 1,950,625（**1.99×**，非 2.00×）
   - 模型总参数 18,100,050 → 21,593,202（**仅 +19.3%**，因为 embedding 占 88.1%）
   - 这与论文 Table 5 的口径完全对得上（换算后）
2. **延迟的绝对量级与论文一致**：论文 FCN𝑝 5.11ms（RTX 4090，单样本），
   我们实测 0.0014 ms/sample = 1.4 μs/sample。
   **注意：这不矛盾**，因为论文的 5.11ms 很可能含 embedding 查表 + Python 开销，
   而我们是纯 GPU 前向 + batch 16384 摊薄。**必须声明测量口径，不能直接比大小。**
3. **诚实结论**：「在本实验的测量协议下（batch 16384、纯 GPU 前向），
   交叉网络宽度变化对端到端延迟的影响低于本测量的分辨率，未能复现论文报告的 23% 延迟差异。
   原因分析：embedding 查表占模型参数 88.1% 但计算量近零，其访存开销淹没了交叉网络的计算差异。」

### ❌ 不能说的
1. 不能说「论文的 23% 是错的」——我们**测不出**，不等于它**不存在**。
   论文可能用了不同协议（如 batch=1、含 Python 开销、含 embedding）。
2. 不能说「r 越小延迟越低」——数据不支持（r=0.75 最慢，r=1.0 最快，是噪声）。
3. 不能把 1.4 μs 和论文的 5.11 ms 放一起比大小——口径不同（差 3000 倍，
   一看就知道不是同一个东西在比）。

## 四、论文自己的 23% 与 Table 5 的矛盾（这条才是硬发现）

论文正文/摘要三处说「延迟降约 23%」，但其 Table 5 四个可比比值是：

| 对比 | 计算 | 结果 |
|---|---|---|
| Criteo ECN → ECN-full | (3.62−2.85)/2.85 | **+27.02%** |
| Criteo FCN𝑝 → FCN𝑝-full | (6.54−5.11)/5.11 | **+27.98%** |
| KKBox ECN → ECN-full | (17.77−13.54)/13.54 | **+31.24%** |
| KKBox FCN𝑝 → FCN𝑝-full | (34.41−27.15)/27.15 | **+26.74%** |

**四个比值没有一个落在 23%±1pp 内。** 这是论文内部的数字不一致，与我们的测量无关，
**是纯文本核算就能确认的硬事实**（analyst 已逐字核实原文与页码）。

→ **报告里这一条要作为主证据**，比我们的延迟实测更有力，因为它不依赖我们的硬件与协议。

## 五、给 runner 的更新指示

**E4-B 的「延迟」这一列，改为报以下三项，且都必须标明口径**：
1. `latency_full_forward_ms_per_sample`（batch 16384，纯 GPU 前向，warmup 50，9 次中位数）
2. `latency_embedding_only_ms_per_sample`（分离测量）
3. `latency_cross_only_ms_per_sample`（分离测量）

并在表下注明：
> 「因 embedding 查表占参数 88.1% 且计算量近零，交叉网络宽度变化对端到端延迟的影响
> 低于本测量分辨率，故延迟列仅报实测值，不据此宣称 LCA 的延迟收益。」

**结论重心移到「参数量」**——那是确定性的、可严格验证的、与论文可对照的。
