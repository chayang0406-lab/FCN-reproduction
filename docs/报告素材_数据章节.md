### 为什么第 6 条是最有信息量的一条

md5 只能回答「文件有没有坏」，**不能回答「这份数据是不是按论文的口径切出来的」**。

如果切分方式是随机切而非分层切，三份的 CTR 必然出现可见差异（大数定律下，
每份 458 万样本，CTR 的抽样标准差约 0.02 个百分点，差异会被清楚观测到）。
而实测三份 CTR **精确到小数点后 4 位完全相同**，valid 与 test 的正例数**同为 1,174,544**，
这是 `StratifiedKFold(10, shuffle=True, random_state=2018)` 强制对齐标签比例的必然结果。

**所以第 6 条把"数据没坏"升级成了"数据是按论文方法切出来的"。**

> 建议表述：「除文件级校验外，本文进一步用标签分布作为切分口径的证据：三份子集的
> 正例比例精确相等（25.6223%），验证集与测试集正例数均为 1,174,544。这与
> StratifiedKFold 分层抽样的性质一致，说明该数据集的分割方式与原始论文口径相同，
> 而非重新随机切分。」

### 3.4 怎么向读者解释 raw/vocab 这两列的差异（重要）

**C 字段 raw/vocab 全部 < 1（0.60–0.98）**，这是**正确**的：1M 抽样里能见到的不同取值，
必然少于全量。若某 C 字段 raw/vocab > 1 且差距很大，反而是异常信号。

**I 字段 raw/vocab 远大于 1（最大 I5 = 368 倍）**，这**也**是正确的，但原因完全不同：
I 字段是连续数值，raw 数的是「未 bucketize 的原始不同数值个数」（浮点数当然多），
vocab 数的是「bucketize 后的桶数」。**两者本来就不该接近。**

> **建议表述**：「I 字段的原始取值个数与 bucketize 后的词表规模不具可比性：
> 前者是连续数值的不同取值数，后者是分桶后的离散取值数。表中并列展示是为了
> 说明分桶的压缩效果，而非用于相互校验。」

## 4. CTR 声明段落（**可直接粘贴，必进报告**）

> ### 数据分布的重要说明
>
> 本文使用的 `reczoo/Criteo_x4` 是经过**负样本下采样**的平衡版本，正例比例为
> **25.6223%**（train/valid/test 三份完全一致）；而原始 Criteo 广告点击数据的
> 点击率约为 **3%** 量级。
>
> 因此，本文报告的 **AUC 与 LogLoss 仅在下采样分布下可比**，不能直接外推到
> 工业原始分布。下采样会减少负样本数量，从而使 AUC 相对原始分布**偏高**，
> 倘若把本文的 0.81 量级 AUC 解读为「工业可用水平」，是不准确的。
>
> 这一限制不影响本文的复现对照结论：由于我们与原文使用**完全相同的数据集版本
> 与切分方式**（三份子集正例比例精确相等，见 2.6 节），两者的比较是在同一分布下进行的，
> 因而是公平的。

**为什么这段必须写（给 writer 的说明）**：

1. **不写会被判为"不准确"**。课程评分要求「完整、准确」，把下采样数据的 AUC
   说成工业水平，是实质性的错误陈述。
2. **写清楚反而是加分项**。它证明作者读懂了数据集性质，而不是"跑完就报数字"。
   这正好落在「与原文的对比分析」这个评分点上。
3. 段落做了三件事：**承认限制 → 说明来源 → 说明为何复现对照仍然成立**。
   很多同学只做到第一件（写"本实验有局限"），不做第三件，读起来像在自我否定。

### 5.2 被证伪的 4 个加速假设（**这段体现工程判断力，建议保留**）

面对 4 GB / 1 MB/s 的传输，先后验证了四种"更快"的方案，全部证伪：

| 假设 | 实测 | 结论 |
|---|---|---|
| 多流并行能提升总带宽 | 4 路并行**合计 1.01 MB/s**，与单流 1.05 无差别 | ❌ 瓶颈是**链路总带宽**，不是单流限速 |
| 换更快的加密算法 | `aes128-ctr` 1.04、`aes128-gcm` 1.07 | ❌ 与默认无差别，瓶颈不在 CPU |
| `ssh -C` 压缩能突破带宽墙 | 全零数据 0.84 → **6.76 MB/s**（8× 提升） | ✅ 机制有效，但**对已 DEFLATE 压缩的 zip 无效** |
| 先重压缩再传更省时间 | bz2 总 60 min vs 直传 64 min；lzma 总 278 min | ❌ bz2 收益可忽略，lzma 慢 3.3 倍 |

> **建议表述**：「针对 4 GB 数据在约 1 MB/s 链路上的传输，本文验证了四种加速方案。
> 其中多流并行与更换加密算法均无收益，说明瓶颈位于链路总带宽而非单流限速或 CPU；
> `ssh -C` 压缩在可压缩数据上有效（8 倍），但对已压缩的 zip 无效；重压缩的
> 时间收益被压缩耗时所抵消。最终采用单流分块传输配合断点续传。」

### 5.3 断点续传的实际价值（**不要写成"可能有用"，要写成事实**）

在 86 分钟的传输窗口内，**实际发生 1 次连接中断**：
```
22:02  Connection closed by 223.113.240.64 port 10188
       此时已传输 2,281,701,376 字节（56%）
```
采用 128 MB 分块 + 逐块 md5 + 状态文件续传，中断后**直接跳过 17 个已完成块**，
损失为 0。若采用单次流式管道，则需从零重传，代价为 56 分钟。

> **建议表述**：「跨网络传输 GB 级数据时，中断不是假设风险而是实际发生的事件：
> 本文传输期间发生 1 次对端连接关闭，发生在已完成 56% 时。分块传输与状态记录
> 使该次中断的额外代价降为零。」

### 5.4 h5 的空间开销（**工程权衡，写进报告**）

fuxictr 将离散特征存为 **int64**、标签存为 **float64**（实测，非推测）：

```
39 字段 × 8 字节(int64) + Label 8 字节(float64) = 320 字节/行   ← 实测精确 320.0
全量 45,840,617 行 → 约 14.67 GB（实测 train 11.735 + valid 1.467 + test 1.467）
若改用 int32 + float32 → 约 7.3 GB
```

> **注意一个易犯的表述错误**：不要写成「Label 4 字节(float32) → 316 对齐到 320」。
> 实测 Label 是 **float64（8 字节）**，所以直接就是 320，不涉及对齐。

> **建议表述**：「特征词表最大规模为 154,564（C21），远小于 int32 上限 2.1×10⁹，
> 因此 int32 足以表示全部特征 ID。但 fuxictr 统一采用 int64 存储特征、
> float64 存储标签，使 h5 体积达到约 14.67 GB，约为 int32/float32 方案（7.3 GB）
> 的两倍。这属于框架层面的**用存储空间换取实现简单性**的工程取舍；
> 在当前磁盘条件下（共享盘可用约 138 GB）该开销可以承受，因此未作修改。」

## 6. 一个可写进报告的"发现"（论文与代码不一致）

论文正文 §6.1.2 表述数值特征按 `⌊log2(x)⌋` 离散化，但作者代码
（`fuxictr.datasets.criteo.FeatureProcessor`）实际执行的是
**`⌊(ln x)²⌋`**（自然对数的平方）。

**判定依据（理论上界，一行可验，不依赖任何数据抽样）**：

| 规则 | x ∈ [0, 10⁶] 时的理论上界 | 能否产出作者日志的 I1 = 44 |
|---|---|---|
| `⌊log2 x⌋` | `⌊log2(10⁶)⌋ = 19` | ❌ **不可能**，上界只有 19 |
| `⌊(ln x)²⌋` | `⌊(ln 10⁶)²⌋ = 190` | ✅ 可以 |

**所以作者日志的 I1 = 44 只可能来自 `⌊(ln x)²⌋`，论文正文的表述有误。**

### 直接从源码与实测双重确认（比推理更硬）

**源码**（`fuxictr/datasets/criteo.py:23-30`，fuxictr 2.0.1 实际安装版本）：

```python
def convert_to_bucket(self, df, col_name):
    def _convert_to_bucket(value):
        if value > 2:
            value = int(np.floor(np.log(value) ** 2))   # ← np.log = 自然对数
        else:
            value = int(value)
        return value
    return df[col_name].map(_convert_to_bucket).astype(int)
```

**实测**（用同一函数逐点求值）：

| x | 1 | 10 | 100 | 10³ | 10⁴ | 10⁵ | 10⁶ |
|---|---|---|---|---|---|---|---|
| `⌊(ln x)²⌋` | 1 | 5 | 21 | 47 | 84 | 132 | **190** |
| `⌊log2 x⌋` | 0 | 3 | 6 | 9 | 13 | 16 | **19** |

穷举整数 x ∈ [0, 10⁶] 可得**不同桶值共 191 个**（0…190），
**远大于 I1 的 vocab_size 44 所需，也严格大于 log2 的上界 19。**

> **建议表述**：「本文在复现过程中发现论文正文与作者实现存在一处不一致：
> 论文 §6.1.2 称数值特征按 ⌊log₂x⌋ 离散化，但作者实现的
> `fuxictr.datasets.criteo.FeatureProcessor` 使用的是 ⌊(ln x)²⌋。
> 判定依据是理论上界：当 x ∈ [0,10⁶] 时 ⌊log₂x⌋ 至多产生 19 个不同取值，
> 而作者日志记录 I1 的 vocab_size 为 44，故只可能来自 ⌊(ln x)²⌋。
> 本文以**作者代码**为准，因为复现的目标是作者的实际实验而非论文文字；
> 采用 ⌊log₂x⌋ 会使 I1 的词表规模降至 12–19，导致整条数据管道与作者不一致。」
>
> **这是"解题思路"与"测试及分析"两处的加分点**：它说明我们不是机械照抄论文，
> 而是通过交叉验证发现了原文的错误，并且做了正确的取舍。

## 7. 数据管道的两个"坑"（体现实现过程的严谨性）

### 7.1 `FeatureProcessor` 必须用 Criteo 版

官方 `run_expid.py` 存在导入覆盖：

```python
from fuxictr.preprocess import FeatureProcessor          # 通用版
from fuxictr.datasets.kkbox import FeatureProcessor      # ← 把上一行覆盖了
```

而 Criteo 配置要求处理 I 字段的 `convert_to_bucket`，**KKBox 版没有这个方法**，
必然报 `AttributeError: 'FeatureProcessor' object has no attribute 'convert_to_bucket'`。

作者自己没有踩到，因为其日志的 `data_format=h5`，跳过了 CSV 预处理阶段。
**我们走 CSV→h5 路径，因此必然遇到。**

正确写法：`from fuxictr.datasets.criteo import FeatureProcessor`

> 实测佐证：`datasets.criteo` 有 `convert_to_bucket`，而 `preprocess`（通用）、
> `datasets.kkbox`、`datasets.avazu` 均没有。

### 7.2 解压完成的判定不能看文件大小

解压 8.9 GB 的 `train.csv` 需要数分钟，中途读取会得到正常增长的半成品
（实测中途读到 6,069,616,640 字节，而最终为 8,917,742,608）。
若据此判为"截断"，会触发一次 64 分钟的无谓重传。

**可靠判据**（两个，推荐第一个）：

```bash
# 判据 1：unzip 会恢复 zip 内的原始时间戳
```
