## 0. 一页结论（给非专家看）

一句话：**环境已经装好，并且 FCNv2 真的在海光 DCU 上完成了一次前向传播 + 反向传播，梯度全部算出来了。**

怎么证明「真的跑了」而不是「装好了就宣布成功」？我没有只看「训练脚本没报错」，
而是抓住模型跑完反向传播之后，把**全部 83 个参数张量的梯度逐个检查了一遍**：

| 检查项 | 结果 |
|---|---|
| 参数张量总数 | 83 |
| 拿到梯度的参数个数 | **83（全部）** |
| 梯度里有非零值的参数个数 | **83（全部）** |
| 梯度里出现 NaN / Inf 的参数个数 | **0** |
| 全局梯度 L2 范数 | **0.304920** |

**人话解释**：反向传播的作用是「算出每个参数该往哪边调、调多少」，算出来的这个东西叫梯度。
如果只把模型搭起来、不做反向传播，那 83 个参数的梯度会全是 `None`（空）。
如果反向传播算了但算崩了（数值爆炸），梯度里会出现 `NaN`（不是一个数）或 `Inf`（无穷大）。
现在 83 个参数**全部**有梯度、**全部**含非零值、**一个** NaN 都没有 —— 这说明反向传播真跑通了，
不是「看起来跑通」。

另外还跑完了完整的 1 个 epoch 训练（含验证集评估），AUC 0.4999 ——
这个数字接近 0.5 是**对的**，因为用的是随机合成数据（标签和特征无关，模型学不到东西）。
合成数据只用来验证「管道能通」，不用于任何精度结论。

**关于 cgroup 的一个坑（值得写进报告）**：
第一次探测时我用 `cat /sys/fs/cgroup/cpu.max` 和 `/sys/fs/cgroup/memory.max`，
两个都返回「文件不存在」，差点得出「没有资源限制」的错误结论。
实际这台机用的是 **cgroup v1**（不是 v2），正确路径是：
- v2 写法：`/sys/fs/cgroup/cpu.max`（内容形如 `600000 100000`）
- **v1 写法（本机实际）**：`/sys/fs/cgroup/cpu/cpu.cfs_quota_us` + `cpu.cfs_period_us`

而且这些 cgroup 文件是**只读挂载**（`mount` 输出里全是 `ro`），
所以 `nproc` 报告 32 核，但实际只能用 6 核的算力。**不要用 `nproc` 判断可用算力。**

> 补充一个反直觉的实测现象：`os.sched_getaffinity(0)` 也返回 **32**（不是 6），
> 且用 `multiprocessing.Pool(32)` 跑 32 个进程各忙等 0.3 秒，总耗时 0.42 秒
> ——**看起来像真的有 32 核**。原因是 CPU 配额（quota）机制是「限速」不是「限核数」：
> 允许你把任务同时铺到 32 个核上，但每 100 ms 周期内所有核加起来只能用 600 ms 的 CPU 时间。
> 短时突发任务能跑满 32 核，**持续负载会被压到 6 核等效**。
> 所以判断「能并行多少」要看 quota，不能看 affinity 或短时测速。

### 2.1 sklearn 必须锁 1.4.2，不能更高（已实测验证）

**这不是猜的，是查了源码 + 跑了真实调用验出来的。**

fuxictr 2.0.1 的 `metrics.py` 第 30 行：

```python
return_dict[metric] = log_loss(y_true, y_pred, eps=1e-7)
```

而 sklearn 从 **1.5.0 起删掉了 `log_loss` 的 `eps` 参数**。实测签名对照：

```
sklearn 1.5.2（错误版本）: (y_true, y_pred, *, normalize=True, sample_weight=None, labels=None)
                          ↑ 没有 eps，传 eps= 会 TypeError
sklearn 1.4.2（正确版本）: (y_true, y_pred, *, eps='auto', normalize=True, sample_weight=None, labels=None)
                          ↑ 有 eps，可用
```

真实调用验证（sklearn 1.4.2）：
```
log_loss([0,1,1,0], [0.1,0.9,0.8,0.2], eps=1e-7) = 0.164252033486018   ✓ 不报错
```

会伴随一条 `FutureWarning`（提示 eps 在 1.5 将被移除），**这条警告可以忽略，不影响结果**。

> 我最初装的是 1.5.2，正是因为 captain 提前踩过这个坑，才没在这里浪费时间。
> 装上 1.5.2 后重装 1.4.2，numpy 仍然是 1.25.0，**没有被带动升级**（已验证）。

### 2.2 polars 有一条 CPU 指令集警告（可用，但要留痕）

```
RuntimeWarning: Missing required CPU features.
The following required CPU features were not detected: pclmulqdq
Continuing to use this version of Polars on this processor will likely result in a crash.
Install the `polars-lts-cpu` package instead of `polars` to run Polars with better compatibility.
```

**实测结论：能用。** 我做了一次真实的 group_by + agg + sort：
```
shape: (3, 2)
┌─────┬─────┐
│ b   ┆ a   │
│ --- ┆ --- │
│ str ┆ i64 │
╞═════╪═════╡
```

贸然换版本会引入新变量。

### 3.2 本地下载 wheel

在本地 Windows 用 `py -3 -m pip download` 指定目标平台的 wheel（不装到本机）：

```powershell
py -3 -m pip download --only-binary=:all: --platform manylinux2014_x86_64 `
   --python-version 311 --implementation cp --abi cp311 -d <dir> <包名...>
```

**关键：`--platform manylinux2014_x86_64 --python-version 311 --abi cp311` 三个参数缺一不可**，

### 7.3 旧版参数量：只能给经验式，结构未确定（含一次被推翻的推导）

> **⚠️ 本节在 2026-11-18 21:xx 被再次修订。** 上一版（21:0x）声称
> 「旧版每层 = `w(D×D/3) + b(D)` = 130,416，6 层 → 16,138,194，**残差 0**」，
> 并说「已彻底消解」。**这个结论是错的，是单点巧合。** 详见下方复盘。

#### (1) 复盘：D//3 公式为什么看起来成立、实际不成立

它只对 ECN=3/LCN=3 这一个点成立。拿其余 13 份旧版日志一验就崩：

| 5 | 15,877,362 | 16,088,274 | **NO** |
| **6** | **16,138,194** | **16,138,194** | **YES（唯一相交点）** |
| 7 | 16,399,026 | 16,188,114 | **NO** |

| 9 | 16,920,690 | 16,287,954 | **NO** |
| 10 | 17,181,522 | 16,337,874 | **NO** |

斜率对比更直接：D//3 公式隐含「每加一层、双网络合计 +260,832」，
而 14 份日志实际斜率只有 **49,920**——**差 5.2 倍**，不可能是同一结构。

**我当时的错误方法**：只有一个观测点（L=6）时，去反解「每层是多少」，
可以得到无穷多种自洽解释，我挑了 `D//3` 这个看起来最"自然"的。
**正确做法是先验证它在其他点上是否也成立。** 教训：单点拟合不能当结构推导。

#### (2) 真正能确定的：经验线性律（14 份日志 / 13 个配置 全部命中）

对 `checkpoints/Criteo_x4_10_h5/` 下**全部 14 份旧版日志**（13 个不同配置，
(3,3) 重复跑了两次，L 覆盖 4–10）做线性拟合：

```
total = 15,838,674 + 49,920 × (ECN_layers + LCN_layers)
```

**13/13 个不同配置全部逐位命中，残差全 0**（验证脚本 `tools/explain_old_params.py`）。

#### (3) 为什么到此为止、不继续反解结构

- **旧版源码不在本仓库**。`git log --all -- src/FCNv2.py` 只有 1 次提交
  （`514a453 first commit to KDD'26`），仓库从未包含旧版实现。
- **旧日志来自另一个项目**。日志内 `Load best model` 路径为
  `/root/autodl-tmp/model_zoo/DCNv3/DCNv3_torch/checkpoints/...`，
  即 **DCNv3_torch**，不是本 FCN 仓库。
- **只有参数量一个观测维度**，无法唯一确定层次结构。
  `49,920 = 2 × 40 × 624`，这个「40」没有任何自然结构解释；
  强行编一个「每层 40 维」的说法是编数据，不做。

**结论**：旧版只给**经验式**（可用于校验旧日志），**明确标注结构未确定**，
不给结构性解释。新版（HEAD）才是结构推导，见 7.4。

#### (4) 旧版与新版不可比

旧日志用的是 `ECN_num_layers` / `LCN_num_layers` 体系（各自计数，3/3 = 6 层），
**不是 exp/lin 体系**。两者不是同一模型的不同配置，是**不同实现**。
所以**旧日志的 AUC 不能与 HEAD 配置的 AUC 当作"同模型不同层数"来比较**，
只能当作「作者公布过的历史参考值」。这一条直接约束了 7.7 的表述。

#### (5) 正确的参数量工具

`tools/param_formula.py`：
- `count_params(exp, lin, ...)` —— HEAD 结构推导闭式公式，**24/24 命中作者日志**
- `count_params_old_impl(ecn, lcn)` —— 旧版经验式，**14 份日志（13 个配置）全部命中**
- `check_model_params(model, expect)` —— runner 跑完实验直接核对实际参数量

用途：runner 每次实验后独立校验「实际模型参数量是否与该配置相符」。
对不上就说明配置未生效 / 代码被改动 / feature_map 不匹配。这是防「跑错配置还不知道」的最后一道闸。

### 7.4 为什么复现基准必须改

#### (1) 参数量对照表

HEAD 代码下，`参数量 = 910,747×16 + 2 × (层数 × 195,936 + 625)`，
其中每层 = 624×312 + 312 + 312 + 624 = **195,936**，单网络 = 层数 × 195,936 + 625：

| 配置（exp / lin） | 总层数 | 总参数量 |
|---|---|---|
| 4 / 1 ← **HEAD 默认** | 5 | **16,532,562** |
| 4 / 2 | 6 | 16,924,434 |
| 3 / 3 | 6 | 16,924,434 |
| 4 / 5 | 9 | 18,100,050 |
| 4 / 0 或 0 / 4 | 4 | 16,140,690 |
| 旧版（ECN 3 / LCN 3） | 6 | **16,138,194** ← 作者主日志，HEAD 复现不出 |

> 交叉验证：`sum(vocab_size) = 910,747` 与论文 Table 2 的 Criteo #Features 完全一致，
> 说明我们对 embedding 参数的算法与作者同口径。这一条把「参数量对账」的可信度坐实了。

#### (2) 证据链

1. 作者主日志 `Params` 块字段名 = `ECN_num_layers` / `LCN_num_layers`（旧）
2. HEAD `src/FCNv2.py` 签名只有 `exp_num_layers` / `lin_num_layers`，无 ECN/LCN
3. HEAD `config/model_config.yaml` 的 `FCNv2_Criteo` = `exp_num_layers: 4` / `lin_num_layers: 1`

### 7.7 ⚠️ 术语纪律：「配置敏感性」≠「种子噪声」

初版曾把 _017 高于主日志 0.000253 说成印证「噪声区间」。**这个措辞不准确，已限定。**
两者是不同的东西，报告中必须分开表述：

| 概念 | 定义 | 本任务能否测得 |
|---|---|---|
| **配置敏感性** | 同模型、**换层数/换超参**导致的指标波动 | ✅ 可由作者日志观察（本文档 7.6） |
| **种子噪声** | 同超参、**同层数**、只换随机种子导致的指标波动 | ❌ **只能靠我们在 DCU 上自己跑**（t6 任务） |

本文档 7.6 里观察到的波动属于**配置敏感性**，因为涉及的两份日志层数不同
（_017 是 exp=4/lin=2，主日志是旧版 3/3）。实测差值逐列分开看：

| 日志 vs 主日志 | valid 差值 | test 差值 |
|---|---|---|
| `_016`（exp=4/lin=1，E0） | **−0.000072** | **+0.000046** |
| `_017`（exp=4/lin=2） | +0.000119 | +0.000253 |
| `_025`（exp=5/lin=5） | +0.000162 | +0.000219 |

> **⚠️ 注意第一行：E0 相对主日志，valid 是 −0.000072（变差），test 是 +0.000046（变好）。
> 符号相反！** 如果混用两列，会得出完全相反的「改进/退化」结论。
>
> **但这个对比只能当「方法论示例」，不能当性能结论。** 原因（captain 2026-11-18 指出）：
> 主日志是旧架构（`ECN/LCN` 体系、6 层、实现不同），E0 是 HEAD 架构（exp=4/lin=1），
> **两者不是同一个模型**，所以「E0 比主日志好/差」这个命题本身不成立。
> 它的正确用途是：**证明「valid/test 混列会导致方向反转」这一方法论风险**，
> 而不是说明任何性能优劣。写报告时请照此标注。

四条日志的极差：**valid 0.000234 / test 0.000253**。
这个量级（万分之二）就是「换层数」能造成的波动 —— 量级上与论文所述
「模型间差距仅约 0.15 个百分点（0.0015）」相差约一个数量级，
说明**层数敏感性本身小于模型间差距**，但仍远大于我们关心的改进幅度，
所以 t6 的多种子实验不可省略。

**「噪声基线」这个词在本项目中专指 t6 产出的「同一配置 × N 个种子」的均值±标准差。
在 t6 完成前，任何关于噪声幅度的陈述都必须标注为「配置敏感性」而非「噪声」。**

### 7.8 结论与建议

1. **前置事实文档里「作者参考数字」那一组（16,138,194 / valid 0.815699 / test 0.816099）
   来自旧代码版本的日志**，不是 HEAD 代码 + `model_config.yaml` 跑出来的模型。
   参数量对不上**不是我们配错了**，是架构演进（详见 7.3，残差已归零）。

## 8.5 稳态训练吞吐（排期依据，**不可当作报告的「每 epoch 秒数」**）

> **适用范围声明（必读，2026-11-18 22:3x 追加）**
>
> 本节所有数字**只用于内部排期决策**，**不能写进报告当作「本模型在 DCU 上的每 epoch 秒数」**。
>
> **⚠️ 新增关键限制：这些测量是在共享租户环境下做的，且当时机器并非独占。**
> 实测期间该机同时运行着另一项目的实验（`/root/_perm99.py` 置换检验、
> `hidden_probe.npz` 激活探针等，cgroup 配额仅 6 核，`load average` 一度达 12.17）。
> **按 captain 2026-11-18 的决定：凡在共享负载下测得的 s/epoch，
> 一律标注「共享租户环境，不可作为官方数字」。**
>
> **报告中的正确写法**：用「量级」表述，例如「约 3–5 分钟/epoch 量级」，
> 或等机器空闲后单独重测再给精确值。
>
> **不受影响的部分**：AUC / logloss 这类**收敛性指标**不受快慢影响
> （只取决于训练了多少 step 与是否收敛），可正常使用。
> 受影响的是 `s/epoch`、`samples/s`、`slowdown_x` 这类**时序指标**。

### (1) 台架与设计

- 脚本：`tools/bench_dcu_throughput.py`（captain）、`tools/bench_eval_scaling.py`（infra）
- 数据：合成 h5，**vocab_size 逐字取自作者日志**（合计 910,747），
  保证 embedding 表大小与真实一致 → 参数量实测 **16,532,562**，与闭式公式相符，
  这本身证明台架搭对了
- 配置：作者超参 batch_size=8192, exp=4, lin=1, embedding_dim=16
- 方法：预热 40 batch 后测 120 batch 取均值
- **负载状态：非独占**（见上方声明），故所有时序数字带系统偏高误差

### (2) 稳态单 batch 与 s/epoch（captain 实测，`bench/bench_result.json`）

| 项目 | 数值 |
|---|---|
| 参数量 | **16,532,562** ✅ 与闭式公式一致 |
| 稳态单 batch | **0.0511 s** |
| 推算 s/epoch（4477 批） | **228.6 s**（3.81 min） |
| 作者 RTX 4090 参考 | 182 s |
| **DCU / 4090** | **1.26×** |
| 单种子 20 epoch | 约 **76 min** |
| 7 种子全流程 | 约 **8.9 h** |

**结论：DCU 与 RTX 4090 基本同一量级，7 种子方案时间上完全可行，不必缩减种子数。**

### (3) 一个有分析价值的观察：单步耗时几乎不随 batch 变化

| batch_size | 单步(s) | samples/s |
|---|---|---|
| 512 | 0.0312 | 16,411 |
| 2048 | 0.0319 | 64,107 |
| 8192 | 0.0336 | 243,584 |

batch 相差 **16 倍**，单步耗时只差 **8%**。
说明此时**不是算力瓶颈，而是 kernel 启动开销主导，DCU 大部分时间在空转**。
这条可作报告「效率分析」的真实素材：**batch 越大越划算，8192 是合理选择；
但该台架并未压出 DCU 的算力上限。**

### (4) validation eval 开销（infra 实测，`bench/eval_scaling.json`）

作者日志拆解（`tools/split_train_eval_time.py`，逐 epoch 从时间戳还原）：

| 日志 | train | eval | 合计 | eval 占比 |
|---|---|---|---|---|
| `_016`（exp=4/lin=1） | 190.5 s | **13.3 s** | 203.8 s | 6.5% |
| 主日志（旧版） | 178.9 s | 11.7 s | 190.6 s | 6.1% |

> 顺带修正**前置事实文档**里「eval 约 12 秒」的说法：_016 实测是 **13.3 s**，主日志 11.7 s。
> 两者都在 12 s 附近，但按不同日志分别是 13.3 / 11.7，报告引用时请写明取自哪份日志。

DCU 上 eval 的规模扩展实测（**先预热一次剔除冷启动**，否则首点严重偏高）：

| valid 行数 | batch 数 | evaluate(s) | μs/样本 |
|---|---|---|---|
| 50,000 | 7 | 0.51 | 10.12 |
| 200,000 | 25 | 1.98 | 9.88 |
| 800,000 | 98 | 7.42 | 9.28 |

两点法拟合（最小点↔最大点）与最小二乘**相差仅 0.5%**，结果稳健：

```
evaluate(s) = 0.045 + 9.22 μs × n_samples
→ 真实 valid 4,584,062 → 42.3 s
```

开销构成拆分（同一进程内实测）：

| 组成 | 耗时 | 说明 |
|---|---|---|
| 裸前向（no_grad） | ~4.0 s | 纯 DCU 算力，仅占约 10% |
| sklearn `log_loss` | 1.7 s | 真实规模实测 |
| sklearn `roc_auc_score` | 2.6 s | 真实规模实测 |
| **h5 读盘 + 转 tensor** | **约 34 s** | **主要瓶颈** |

**关键发现：eval 的瓶颈不是 GPU 算力，而是每 epoch 重新读 4.58M×40 的 h5（约 1.5 GB）。**
真正落地时若把 valid h5 常驻内存（或用 `H5BlockDataLoader` 分块），
eval 可以从 42 s 压到 10 s 量级。

### (5) DCU 每 epoch（含 eval）预估 —— runner 排期 E0 应使用的数字

| 项目 | 数值 |
|---|---|
| train = 0.0426 s/batch × 4477 | **190.7 s** |
| eval（完整口径，含 h5 读 + 指标） | **42.3 s** |
| **合计 / epoch** | **233.0 s（3.88 min）** |
| eval 占比 | 18.2% |
| 对照作者 4090（203.8 s） | **1.14×** |
| 单种子 20 epoch | **77.7 min** |
| 7 种子 | **9.06 h** |

> 注意 train 用了 0.0426 s/batch（infra 复测），略低于 captain 的 0.0511 s/batch。
> 差异应在 DCU 负载抖动范围内。**排期建议取保守值**：
> 用 0.0511 → train 228.6 s + eval 42.3 s ≈ **271 s/epoch**，
> 7 种子 20 epoch ≈ **10.5 h**。**按 11 小时排期更稳妥。**

### (6) 为什么这些数不能直接写进报告

1. **合成数据**：虽然 vocab 尺寸真实（参数量已对上），但样本是随机生成的，
   embedding 的**访问局部性**与真实 CTR 数据不同（真实数据高度长尾，热门 ID 反复命中）。
   这会改变显存/缓存行为，进而影响实际耗时。
2. **不含 h5 逐 epoch 重读的真实代价**：真实训练时 train h5 是 36.6M 行（约 12 GB），
   本台架只有 250 万行（790 MB），I/O 压力不可比。
3. **不含 feature_map 构建、checkpoint 读写、早停判定等**。
4. **单卡单进程**，未反映多 seed 并发时的资源争用。

→ **报告里若要写「每 epoch 秒数」，必须在真实 Criteo h5 上实测。**
本节数字的正确用途只有一个：**决定「7 种子方案是否可行」**，答案是可以。

## 8.9 本项目的方法论纪律

> 这些条款不是从书上抄的，每一条都对应本项目实际踩过的一次坑。
> 判定标准：违反其中任何一条，结论一律不得进入报告。

### 纪律 1：单点拟合一概视为欠定，至少用 3 个不同取值点验证

**踩坑实例（infra，2026-11-18）**：仅凭作者主日志一个观察点（总层数 L=6、参数量 16,138,194），
反解出「旧版每层 = `w(D×D/3) + b(D)` = 130,416」，代回得 16,138,194，残差 0。
看起来完美闭合，当时判断为「已彻底消解」。

**拿其余 6 个点一验就崩**：

| 层数和 L | D//3 公式 | 日志实际 | 一致？ |
|---|---|---|---|
| 4 | 15,616,530 | 16,038,354 | NO |
| 5 | 15,877,362 | 16,088,274 | NO |
| **6** | **16,138,194** | **16,138,194** | **YES（唯一）** |
| 7 | 16,399,026 | 16,188,114 | NO |
| 8 | 16,659,858 | 16,238,034 | NO |

斜率对比：D//3 式隐含每层 +260,832，实际斜率 49,920，**差 5.2 倍**。

**为什么单点会骗人**：一个方程解两个未知数（固定项、每层增量）有无穷多组解。
D//3 只是其中一个「看起来自然」的猜测。**残差为 0 并不能证明结构正确，
只能证明这个猜测自洽。**

**执行规则**：
- 任何「拟合出的公式」必须**至少 3 个不同自变量取值**上验证，并且取值要**跨越较大范围**。
- 只有 2 个点也不行（两点必然确定一条直线，无法检验线性假设本身）。
- 单点吻合时，只能表述为「与某点一致」，**不得表述为「已反解出规律」**。

### 纪律 2：验证器本身要被验证

闸门/校验脚本如果不证明「它能拦住错误」，就等于没有闸门。

**执行规则**：
- 任何断言/校验器，必须配一个**故意喂错**的用例，证明它确实报错。
- 本项目实例：`tools/verify_param_gate.py` 除了验证 exp=4/1、4/2、3/3、5/5 参数量正确外，
  还专门测了「按 exp=4/lin=2 建模型、却期望 exp=4/lin=1 的参数量」，
  必须报出 `MISMATCH 实际=16,924,434 期望=16,532,562`。
  若这一步静默通过，说明闸门是坏的。

### 纪律 3：valid 与 test 指标必须分列，且只与同列比较

**踩坑实例（infra，2026-11-18）**：审计脚本对所有 `[Metrics] AUC` 行取全局最大值当
「best AUC」，而日志里 AUC 出现在三处（逐 epoch 验证、训练后 Validation evaluation、
Test evaluation）。因为早停是**看着 valid 挑模型**，best model 在 valid 上「被挑过」，
test 是干净的，**test AUC 系统性略高于 valid AUC**，于是「取最大」几乎总取到 test，
被误标成 valid。

**真实反例（符号相反）**：E0（exp=4/lin=1）相对主日志

| 指标 | 差值 | 方向 |
|---|---|---|
| valid | −0.000072 | 变差 |
| test | +0.000046 | 变好 |

**同一对模型，两个指标的结论方向相反。** 混列会直接得出相反的「改进/退化」结论。

> 注：该对比只作**方法论示例**，不构成性能结论——两者是不同实现（旧日志来自
> DCNv3_torch 项目），"谁更好"这个命题本身不成立。

**执行规则**：
- 报告里 valid 与 test 必须分列成两列，禁止只报一个而不说明是哪个。
- 任何「改进/退化」结论必须**同列内**比较。
- 引用作者数字时必须写明来源文件名与该数字属于 valid 还是 test。

### 纪律 4：区分「确定性指标」与「随机性指标」

| 类别 | 例子 | 需要几次运行 | 理由 |
|---|---|---|---|
| **确定性指标** | 参数量、层结构、单 batch 延迟（同一硬件同一配置） | **n=1 即可** | 给定配置后结果唯一，重复跑不会变 |
| **随机性指标** | AUC、logloss | **必须多样本**，报均值±标准差 | 受随机种子、数据顺序、dropout 影响 |

**为什么这条重要**：本项目 AUC 普遍落在 81.35–81.50，模型间差距仅约 0.15pp。
单次运行的种子波动就可能吞掉这个差距。**因此所有 AUC 类结论必须基于多种子分布检验**，
而参数量这类结论跑一次就够，不必浪费算力重复。

**执行规则**：
- 写结论前先判定它属于哪一类；随机性指标禁止用单次运行下结论。
- 随机性指标报数必须给 n（几个种子）与标准差，不能只给均值。

### 纪律 5：外推必须标注不确定来源，且不得当作实测值写进报告

**踩坑实例（infra，2026-11-18）**：用 5 万行 valid 测 `evaluate()` 耗时 0.52 s，
线性外推到 458 万行得 47.7 s。但 5 万行只有 7 个 batch，
h5 打开/数组分配/sklearn 首次调用等**固定开销**被摊到很少样本上，
每样本成本被严重放大。改用 3 个规模（5万/20万/80万）分离固定与边际成本后，
外推值为 **42.3 s**，且两点法与最小二乘相差仅 0.5%——这才可信。

更早一次：冒烟测试记录「前向+反向 4.370 s」，被误当作单 batch 耗时。
实际那是**首次 kernel JIT 编译**开销，稳态是 **0.0511 s**，**差两个数量级**。

**执行规则**：
- 外推必须写清：①外推依据的实测点 ②不确定来源 ③区间（乐观/悲观）。
- 外推值在报告里**必须标注「估算」**，不得与实测值并列。
- 报告中的「每 epoch 秒数」类数字，必须是真实数据实测值。
- 带冷启动的测量必须先预热再计时；单次计时不得作为稳态值。

### 纪律 6：共享机器上测的时序指标，必须标注负载状态

**踩坑实例（2026-11-18）**：本项目在 DCU 上测吞吐时，该机同时运行着另一项目的实验
（`_perm99.py` 置换检验、`hidden_probe.npz` 激活探针），cgroup 配额只有 6 核，
`load average` 一度达 **12.17**（约超卖 2 倍）。在这种状态下测得的
`s/epoch`、`samples/s`、`slowdown_x` 全部偏高，且**事后无法分辨是「被污染」还是「真这么慢」**。

**关键区分**：

| 指标类型 | 例子 | 受共享负载影响？ | 处理方式 |
|---|---|---|---|
| **时序指标** | s/epoch、samples/s、单 batch 延迟、加速比 | **是，且不可事后校正** | 必须独占测量；否则只报量级 |
| **收敛性指标** | AUC、logloss | **基本不受影响**（只取决于 step 数与收敛） | 可在共享负载下正常做 |
| **确定性结构指标** | 参数量、层结构 | 完全不受影响 | 随时可测 |

**执行规则**：
- 测时序指标前先看 `uptime` / `/proc/loadavg`；`load > 配额核数` 即视为不可用。
- 共享负载下测得的时序值，**必须标注「共享租户环境，不可作为官方数字」**，
  报告中改用「量级」表述（如「约 3–5 分钟/epoch 量级」）。
- 不得为了赶进度而用被污染的时序数字，也不得为了等 clean 环境而停掉整个项目——
  **正确做法是把「时序指标」和「收敛指标」分开处理**。
