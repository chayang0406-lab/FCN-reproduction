## 二、四个缺陷（全部实测复现，含修复）

### P3 崩溃的 run 被永久跳过，且统计静默少算 ★半致命

`run_e0_baseline.py:105` 只用「train.log 非空」判断已完成。**跑崩的 traceback 也是非空**，
于是失败的种子永远不再重跑。

实测（放一个内容是 traceback 的 train.log）：
```
[skip] e0_exp4_lin1_seed2025 已完成
  !! 日志里解析不到参数量，该 run 视为无效
      valid=0.000000 test=0.000000 params=None (NO_PARAMS)
```
summary 里 `failed=false`、`param_check=NO_PARAMS`；`e0_stats.json` 里
**`n_seeds=3` 但只有 2 个 run 参与均值** —— 报告里的 n 会虚报。

**修复**：只有「valid AUC + test AUC + 参数量正确」三项齐备才算完成，
否则把旧日志归档为 `train.log.failed-<时间戳>` 并重跑。

实测修复后：
```
[rerun] e0_exp4_lin1_seed2025 上次未产出有效结果，旧日志归档为 train.log.failed-20261118-215020
      valid=0.510487 test=0.495719 params=16532562 (OK)
```

### P3b 参数量 MISMATCH 不中止，白烧全部种子 ★致命（时间）

真实数据 76 min/seed。若配置没生效，原版会**把 8 个种子全跑完才在最后发现问题**。

实测 3 个种子（全部 MISMATCH）：

| 版本 | 退出码 | 实际启动的 run 数 |
|---|---|---|
| `run_e0_baseline.py` | 0 | **3**（全跑完，白烧） |
| `run_e0_baseline_v2.py` | **2** | **1**（立即中止） |

按 8 种子折算：**原版会白烧 10.1 小时**。

### P4 单轮耗时 / 轮数静默算错 ★致命（数据）

两个叠加原因：

1. `fuxictr.fit()` **只在开头打一次 `Epoch=1 start`**，之后每轮只有 `Epoch=N end`。
   用 start 行做差分 → `secs` 恒为空。
2. 正则用 `^时间戳` 锚行首。但我们把 stderr 也并进 train.log（否则 traceback 会丢），
   而 **tqdm 进度条写 stderr 且不换行**，并流后物理行变成：
   ```
   100%|█████| 1/1 [00:18<00:00]2025-05-13 06:38:23,835 P931074 INFO ... Epoch=1 end
   ```
   时间戳不在行首 → 一条都匹配不到。

实测三份作者日志：

| 日志 | 原版 n_epochs | 原版 mean | 修复后 n_epochs | 修复后 mean |
|---|---|---|---|---|
| `FCNv2_Criteo.log`（旧实现 3+3） | 1 | `None` | 20 | **191.22 s** [189.1, 192.9] |
| `FCNv2_Criteo_016`（E0 基准 4+1） | 1 | `None` | 19 | **204.38 s** [204.0, 205.1] |
| `FCNv2_Criteo_017`（4+2） | 1 | `None` | 21 | 219.73 s [217.6, 220.6] |

**修复**：`epoch_1 = end_1 - start_1`；`epoch_N = end_N - end_{N-1}`；正则不锚行首；
并把 `n_epoch_start_lines / n_epoch_end_lines / epoch_seconds` 全序列写进 summary ——
**让「解析失败返回空列表」能自证，而不是靠人眼看 mean 是 None。**

### G1 `e0_guard.py --summarize` 把无效 run 算进统计 ★致命（结论）

它**自己打印**「这些 run 的结果作废」，但**仍然把它们的数值算进 mean/sd**。

实测（2 个正常 run + 1 个参数量错的 run）：

| 口径 | valid mean | valid sd | 要分辨 0.001 需配对 | δ_min |
|---|---|---|---|---|
| guard 实际输出（含无效） | 0.508137 | 0.007253 | 826 | 0.016592 |
| 正确（剔除无效） | **0.512206** | **0.002430** | **93** | **0.005559** |

**功率分析被放大 8.9 倍**，δ_min 被放大 3 倍。这直接会把「结论写不出来」变成
「结论写错」——报告里若采用 guard 的 δ_min，会把一个本来可分辨的效应判成不可分辨。

`e0_final_summary.json` 顶层也没有 `n_valid / excluded` 字段，下游无法察觉。

**修复建议**：`va`/`ta` 列表过滤时同时要求 `n_params == expect_params`，
并新增 `n_valid / n_excluded / excluded_runs` 三个字段。

## 三、三处需要更正的数字口径（会影响报告）

### 3.1 「191.17 s/epoch」不是 E0 的耗时

captain 消息写「复核作者日志：19 个 epoch，均值 191.2 s/epoch」。实测：

- **191.22 s** 属于 `FCNv2_Criteo.log` —— 这是**旧实现（3 ECN + 3 LCN）**，参数 16,138,194，**不可复现**
- **E0 基准（HEAD 4+1，16,532,562）对应 `_016` 日志，是 204.38 s**，不是 191.2 s

两份日志的 epoch 数也不同（20 vs 19）。**报告里 E0 的 s/epoch 必须写 204.4 s**，
191.2 s 只能作为「旧实现历史参考」。这正好印证 `docs/参考基准.md:313` 的记载。

> 顺带说明：这个差异与「DCU 慢 1.26 倍」的结论不冲突——1.26 倍是对 RTX 4090 的
> 182 s（论文 FCN𝑝），204.4/182 = 1.12，而 DCU 实测 228.6/182 = 1.26。两个数各自成立，
> 但**不能混用**：204.4 是 4090 上 _016 配置的实测，228.6 是 DCU 上合成数据的实测。

### 3.2 交叉网络参数量是「每子网」还是「两子网合计」

captain 给的 4 个数我逐个核算：

| 配置 | 每子网 | 两子网合计 | 对应 captain 的数字 |
|---|---|---|---|
| 4层 r=1/2 | 784,369 | 1,568,738 | 784,369 = **每子网** |
| 4层 r=1 | 1,565,617 | 3,131,234 | 1,560,625（差 4,992） |
| 9层 r=1/2 | 1,764,049 | **3,528,098** | 1,764,049 = **每子网** |
| 9层 r=1 | 3,521,857 | 7,043,714 | 3,510,625（差 11,232） |

实测 9L_r050 的 `n_params_cross = 3,528,098 = 2 × 1,764,049` ✅。
**所以 captain 的数是「每子网」口径**。报告里必须写清口径，否则 1.76M / 3.51M
与实测的 3.53M / 7.04M 对不上，审阅会认为数据错。

### 3.3 r=1.0 参数量比线性外推少 11,232 —— 是设计，不是 bug

实测 9 层四档（每子网交叉参数）：885,145 → 1,764,049 → 2,642,953 → 3,510,625。
前两步增量恒为 878,904，第三步只有 867,672（少 11,232 = 2×9×624）。

已查明原因（`fcn_v2_soft.py:301-342` `_cross_layer`）：**r=1.0 走 `full_rank` 路径，
没有 γ/β**，与 `ECN_full.py` 的 ExponentialCrossNetwork 逐字一致。

- r=0.75（proj=468，有 γ/β）：每层 `624×468 + 2×468 + 624 = 293,592`
- r=1.00（proj=624，无 γ/β）：每层 `624×624 + 624 = 390,000`
- 差额 `(390,000 − 293,592) × 9 = 867,672` ✅ 与实测完全吻合

**这是有意设计，不是漏项**，报告里可以作为「全秩路径省掉两个 D/2 向量」来解释。

## 四、原仓库洁净性

### 4.1 ⚠️ 事故留痕：曾发生 `config.csv` 误写入原仓库根

**这是缺陷，不是正常现象，特此留痕。**

- **根因**：`tools/run_expid_fixed.py:113`
  ```python
  result_filename = Path(args.config).name.replace(".yaml", "") + ".csv"
  ```
  `args.config` 是 `<run_dir>/config/` 目录，`Path(...).name` 得到 `"config"`，
  于是文件名是 `config.csv`；而 `run_e0_baseline.py` 用 `subprocess.run(..., cwd=args.repo)`
  启动，相对路径就落到了**原仓库根** `code/FCN_repo/config.csv`。
- **发现过程**：runner 在验证 `run_improved.py` 路径行为时，顺手 `ls code/FCN_repo/*.csv` 查到。
- **规模**：共 16 行汇总记录（9,326 字节），每条对应一次 run 的 `[val]/[test]` 指标。
- **处置**：已删除。删除前两份留证副本保存在
  `/tmp/config_csv_pollution_evidence.csv`（21:58）与 `/tmp/config_csv_evidence_2210.csv`（22:10）。
- **后续再次出现**：22:10 runner 自己做 G-C 测试时又生成一次（来源同一个 bug），
  说明**只要还用 `run_expid_fixed.py` 就还会重犯**，不是一次性事故。

**为什么这件事性质严重**：整个复现的合法性建立在「原仓库零改动」上。一旦仓库被写入
非源码文件，「我们改了什么」就说不清了——尤其在报告里要声称「我们的 E0 与原仓库逐位一致」时。

### 4.2 洁净性核验：源码逐字节与 tar 一致

删除 `config.csv` 后，用 `code/FCN.tar.gz`（上传时的原始压缩包）解出内容逐文件比对：

```
SAME  README.md
SAME  requirements.txt
SAME  run_expid.py
SAME  run_expid_list.py
SAME  run_param_tuner.py
SAME  test.py
SAME  config/
SAME  src/ECN.py  src/ECN_full.py  src/FCNv1.py  src/FCNv1_full.py
      src/FCNv2.py  src/LCN.py  src/__init__.py
唯一差异：src/__pycache__/（Python 自动生成的字节码，运行产物，不是源码改动）
```

→ **原仓库所有源码文件与 tar 逐字节一致，未发生任何源码改动。**
唯一差异 `__pycache__/` 是 Python 导入时自动生成的 `.pyc` 缓存，不参与版本对照。

### 4.3 建议的根治办法（二选一）

1. 改 `run_expid_fixed.py`：把 `result_filename` 落到 `out_dir`（`--result-json` 所在目录）；
2. 或在 driver 里把 `cwd` 设成 run 目录，而不是 `args.repo`（注意 `import src` 需要
   `sys.path`，`run_expid_fixed.py` 已用 `--repo` 显式加路径，所以改 cwd 不影响导入）。

**开跑前建议再查一次**：`ls $P/code/FCN_repo/*.csv` 应无输出。
