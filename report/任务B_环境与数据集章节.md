## 4.1 硬件与软件环境配置

### 4.1.1 硬件：为什么用国产加速卡

本实验全部在**海光 DCU K500SM_AI** 上完成。选择它的原因不是"更方便"，
而是**这台机器是课题组能拿到的唯一一块可用加速卡**，这也决定了本项目的两个现实约束。

| 项目 | 实测值 | 怎么得到的 |
|---|---|---|
| 加速卡型号 | 海光 DCU K500SM_AI | `torch.cuda.get_device_name(0)` |
| 架构标识 | `gfx928:sramecc+:xnack-` | `torch.cuda.get_device_properties(0).gcnArchName` |
| 计算单元数 | 120 CU | 同上 |
| 显存 | **63.98 GiB** | 同上 |
| CPU 配额 | **6 核**（cgroup 限制） | 读 cgroup 的 `cpu.max` |
| 内存配额 | **115 GB**（cgroup 限制） | 读 cgroup 的 `memory.max` |

> **一个必须说明的事实**：这台机器是**共享租户**环境，同一个 cgroup 内同时运行着
> 其他不相关的任务（实验期间实测 load average 曾在 2.4 到 20.6 之间波动）。
> 这直接影响本报告对**时序指标**（每轮耗时、总训练时间）的解读——见 5.7。

### 4.1.2 软件栈：三个版本锁，每一个都踩过坑

| 组件 | 版本 | 为什么必须是这个版本 |
|---|---|---|
| DTK | 26.04 | 海光官方工具链，`source /opt/dtk-26.04/env.sh` 后 torch 才认识 DCU |
| PyTorch | 2.7.1+das.opt1.dtk2604 | 海光定制版；上游官方版本无法调用 DCU |
| Python | 3.11.9 | 系统 `/usr/local/bin/python3` |
| **scikit-learn** | **1.4.2（必须锁）** | 见下面的坑 |
| **numpy** | **1.25.0（必须锁）** | 见下面的坑 |
| fuxictr | 2.0.1 | 作者指定的框架版本 |

#### 坑一：scikit-learn ≥1.5 会让训练在第 2 轮之后崩溃

这个坑非常隐蔽，因为它**不在第 1 轮暴露**。

**机制**：fuxictr 在每轮结束后用 `sklearn.metrics.log_loss` 算 logloss。
scikit-learn 1.5.0 版本**移除了 `log_loss` 的 `eps` 参数**。
而 fuxictr 2.0.1 的代码里仍在传这个参数：

```python
# fuxictr 内部
log_loss(y_true, y_pred, eps=1e-7)     # ← 1.5+ 版本会抛 TypeError
```

**为什么第 1 轮不崩**：fuxictr 的评估流程是"先算 AUC（能正常算），
第 1 轮结束时只报 AUC 不报 logloss"，到第 2 轮才真正调用 `log_loss`。

**实际现象**：
```
Epoch=1 跑完，正常打印 AUC 0.804883
Epoch=2 跑到一半，突然 TypeError: log_loss() got an unexpected keyword argument 'eps'
```

**后果**：一个已经跑了 4 分钟的 epoch 白费，而且**看起来像是"第 2 轮才出的问题"**，
排查时会误以为是数据或模型的问题。

**解决**：`pip install scikit-learn==1.4.2`。

> **这个坑的一般形式**：依赖库的**次版本升级**可能移除不兼容参数，
> 而框架代码没跟着更新。这类问题的特点是**延迟暴露**——
> 前几轮正常，后面才崩，让人以为是自己代码的问题。

#### 坑二：numpy 2.x 与 fuxictr 2.0.1 不兼容

numpy 2.0 移除了一批 `np.float_` 之类的旧别名，fuxictr 2.0.1 里还有引用。
表现为导入阶段就报 `AttributeError`。锁 1.25.0 即可。

#### 坑三：这台机器"有外网"，但需要 source 一个脚本（**此前的判断错了**）

这一点值得单独写，因为**它让我们白走了两小时的弯路**。

**此前的错误判断**：项目初期实测 `curl https://pypi.org` 失败，
于是认定"这台机器没有外网出口"，制定了整套离线方案：
本地用 `pip download --platform manylinux2014_x86_64` 下载 wheel → 压缩上传 → `pip install --no-index`。

**实际情况**：

```bash
source /root/private_data/.ai_user_info/ai_proxy
# 之后 github.com / pypi.org / huggingface.co 全部 HTTP 200
```

这个脚本设置的是**带认证的 HTTP 代理**（`http://<user>:<pass>@10.15.100.43:3120`），
`no_proxy` 里排除了 `*.ksai.scnet.cn`（集群内部访问不走代理）。

**为什么当时没发现**：直接 `curl` 时环境里没有 `http_proxy` 变量，
浏览器式的访问方式自然失败。而集群里其他项目的下载脚本（如 `/root/dl_coco.sh`）
**第一行就是 `source` 这个文件**——线索一直在，只是没去看。

**影响**：三个数据集（共 2.5 GB）如果用离线方案要从本地传，
按实测 0.9–2 MB/s 的上传速度需要 20–45 分钟；而用外网直接下载只用了 5 分钟。

> **这条教训写出来是为了给后来者省时间**：
> **"没网"这个结论必须验证到"连代理也没有"才算成立**，
> 而不是"直接 curl 失败"就下结论。

## 4.2 数据集介绍

### 4.2.1 论文用了 6 个数据集，我们做 3 个（分工说明）

论文在 **six CTR prediction datasets** 上评测：Avazu、Criteo、ML-1M、KDD12、iPinYou、KKBox
（原文 6.1.1 节）。本项目为两人合作，数据集按**总训练耗时对等**分工：

| 数据集 | 实例数 | 字段 | 特征数 | 相对 Criteo 的数据量 | 归属 |
|---|---|---|---|---|---|
| Criteo | 45,840,617 | 39 | 910,747 | 1.00× | **本组（任务 B）** |
| Avazu | 40,428,967 | 24 | 3,750,999 | 0.88× | **本组（任务 B）** |
| iPinYou | 19,495,974 | 16 | 665,765 | 0.43× | **本组（任务 B）** |
| KKBox | 7,377,418 | 13 | 91,756 | 0.16× | 另一组（任务 A） |
| ML-1M | 739,012 | 7 | 9,751 | 0.02× | 另一组（任务 A） |
| KDD12 | 141,371,038 | 13 | 4,668,096 | 3.08× | 另一组（任务 A） |

> **为什么这样分**：KDD12 的数据量是 ML-1M 的 **191 倍**，
> 若按"各 3 个"随意分配会严重不均。
> 本组承担的三个数据集合计约 1.05 亿条，另一组合计约 1.49 亿条，
> **在总量上接近对等**（本组还负责 Criteo 的完整复现基线）。

**上述数字全部来自论文 Table 2**，且我们逐个核对过（见 4.2.3）。

### 4.2.2 三个数据集各是什么

#### Criteo（本项目的主数据集）

**来源**：Criteo Display Advertising Challenge（Kaggle 2014），
通过 reczoo 的 `Criteo_x4` 发布版获取。

**它长什么样**：每行是一条广告展示记录，13 个数值特征（I1–I13）+ 26 个类别特征（C1–C26），
标签 `Label` 表示"有没有被点击"。

| 项目 | 值 |
|---|---|
| 总行数 | 45,840,617 |
| 字段数 | 39 个特征 + 1 个标签 = 40 列 |
| 特征取值总规模（Σvocab） | **910,747** |
| 正样本比例（CTR） | **25.6223%** |

> ⚠️ **关于 25.6% 这个 CTR 的重要说明**：
> 真实工业场景的广告点击率通常在 **3% 左右**，25.6% 说明这份数据**做过负样本下采样**
> （把大量"没点击"的样本丢掉了以平衡正负比）。
> **这会让 AUC 被显著抬高**——所以本文报告的 0.8156 不能理解为"工业可用精度"，
> 只能在与论文同款数据的横向比较中有意义。这个边界会在 5.1 再次声明。

#### Avazu

**来源**：Avazu Click-Through Rate Prediction（Kaggle 2014），reczoo `Avazu_x4` 版。

**它长什么样**：移动广告点击日志，字段以类别型为主（站点、应用、设备、时间等）。

| 项目 | 值 |
|---|---|
| 总行数 | **40,428,967** |
| 分片 | train 32,343,172 / valid 4,042,897 / test 4,042,898 |
| 字段数 | 24 |
| 特征取值总规模 | 3,750,999 |

**特点**：特征基数极大（375 万个取值，是 Criteo 的 4 倍），
但每个特征的基数分布与 Criteo 不同。**类别特征占绝对主导**。

> **预处理特殊要求**：论文 6.1.2 说 Avazu 要把时间戳拆成三个新字段
> （hour、weekday、weekend）。这个数据集发布版里已经拆好了。
> 另外 `min_categr_count` 设为 **2**（Criteo 是 10）——因为 Avazu 的类别太稀疏，
> 用 10 会过滤掉过多取值。

#### iPinYou

**来源**：iPinYou 全球 RTB 竞价算法大赛，reczoo `iPinYou_x1` 版。

**它长什么样**：实时竞价（RTB）的广告曝光日志。

| 项目 | 值 |
|---|---|
| 总行数 | **19,495,974** |
| 分片 | **train 15,395,258 / test 4,100,716（无独立 valid）** |
| 字段数 | 16 |
| 特征取值总规模 | 665,765 |

> **一个必须说明的细节**：这个发布版**只有 train 和 test 两个文件，没有 valid**。
> 而作者 `dataset_config.yaml` 里的 `iPinYou_x1_csv` 条目把 `valid_data` 也指向了
> `test.csv`——**与发布版结构一致，不是我们配错了**。
> 这带来一个方法学问题：**验证集与测试集相同，等于用测试集调早停**，
> 会轻微高估精度。**本文如实声明这一点**，并在与论文对比时说明该数据集的数字不可直接比较。

### 4.2.3 行数核对：三个数据集全部与论文精确相符

这是数据完整性的**第一道硬证据**。我们用 `awk 'END{print NR-1}'` 逐文件统计
（减 1 是去掉表头），结果如下：

| 数据集 | 实测合计 | 论文 Table 2 | 差异 | 判定 |
|---|---|---|---|---|
| **Criteo** | 45,840,617 | 45,840,617 | **+0** | ✅ 精确相符 |
| **Avazu** | 40,428,967 | 40,428,967 | **+0** | ✅ 精确相符 |
| **iPinYou** | 19,495,974 | 19,495,974 | **+0** | ✅ 精确相符 |

**三个数据集、合计约 1.05 亿行，全部精确到个位相符。**

> **为什么这条证据重要**：如果下载的数据版本不对（比如用了 `Avazu_x1` 而不是 `Avazu_x4`），
> 行数会立刻不符。**行数是"版本对不对"的最直接判据**，比看文件名可靠。

### 4.2.4 特征取值总规模：第二道硬证据（Criteo 已验）

行数对只说明"样本数对"，不说明"预处理对"。第二道证据是**每个特征的取值个数**。

以 Criteo 为例，我们生成的 `feature_map.json` 里 39 个特征的 `vocab_size`
与作者日志**逐字段完全一致**：

| 特征 | 本文实测 | 作者日志 | 差 |
|---|---|---|---|
| C1 | 1,446 | 1,446 | 0 |
| C3 | 157,339 | 157,339 | 0 |
| C12 | 156,656 | 156,656 | 0 |
| C16 | 148,913 | 148,913 | 0 |
| C21 | 154,564 | 154,564 | 0 |
| I1 | **44** | **44** | 0 |
| ⋮ | （39 个字段全部） | | 0 |
| **Σ(vocab)** | **910,747** | **910,747** | **0** |

**39/39 字段零差异。**

> **`I1 = 44` 这个数字为什么特别重要**：它唯一确定了分桶规则。
> 论文正文写的是 `⌊log2(x)⌋`，但那样 I1 只能产生约 10 个取值（详见 4.3.3）。
> 实测 44 说明**实际实现用的是 `⌊(ln x)²⌋`**。
> **一个数字就能判定用错了哪个公式**——这就是"确定性指标"的威力。

## 4.3 数据预处理与数据集划分

### 4.3.1 整体流程

```
原始 CSV（train/valid/test）
      │
      ├─ ① 类别特征：统计每个取值出现次数
      │     出现次数 < min_categr_count 的 → 归为 "OOV"（out-of-vocabulary，没见过）
      │
      ├─ ② 数值特征：分桶（把连续值变成离散的桶编号）
      │
      ├─ ③ 建立 vocab（每个特征有哪些取值，各分配一个整数 id）
      │
      └─ ④ 转成 h5（fuxictr 要求的高效二进制格式）
             最终产物：feature_map.json + train/valid/test.h5
```

**人话**：把"人看的 CSV"变成"模型吃的整数矩阵"。
中间要做两件事——**把太罕见的取值合并**（不然每个只出现一次的值都占一个 id，浪费），
**把连续数字切成分段的桶**（模型只认整数编号，不认小数）。

### 4.3.2 类别特征：`min_categr_count` 阈值

每个数据集这个阈值不同，来自作者配置（`dataset_config.yaml`）：

| 数据集 | `min_categr_count` | 论文 6.1.2 的说法 |
|---|---|---|
| Criteo | 10 | "threshold to 10 for Criteo, KKBox, and KDD12" ✅ |
| KKBox | 10 | 同上 ✅ |
| KDD12 | 10 | 同上 ✅ |
| Avazu | **2** | "2 for Avazu and iPinYou" ✅ |
| iPinYou | **2** | 同上 ✅ |
| ML-1M | 1 | "1 for the small dataset ML-1M" ✅ |

**这一项论文与代码完全一致，没有分歧。**

**人话**：一个取值在训练集里出现次数少于这个数，就不给它单独的编号，
统一归成 "OOV"（相当于"其他"）。Criteo 用 10，意味着出现不到 10 次的取值全部合并。

> **为什么 Criteo 用 10 而 Avazu 用 2**：Criteo 的类别特征基数大但分布相对集中，
> 用 10 能有效压缩词表（910,747 个值）；Avazu 的取值极其稀疏（375 万个），
> 用 10 会砍掉太多信息，只能用 2。

### 4.3.3 ⚠️ 数值特征分桶：论文正文与代码不一致（三处之一）

**这是本项目发现的第一处实质性不一致，必须写清楚。**

#### 论文正文的说法

> For the Criteo and KDD12 dataset, we discretize the numerical feature fields by
> **rounding down each numeric value x to ⌊log2(x)⌋ if x > 2, and x = 1 otherwise**.

翻译：x > 2 时取 `⌊log2(x)⌋`，否则取 1。

#### 代码的实际实现

来自 `fuxictr/datasets/criteo.py` 的 `convert_to_bucket`：

```python
def _convert_to_bucket(value):
    if value > 2:
        value = int(np.floor(np.log(value) ** 2))   # 自然对数再平方
    else:
        value = int(value)                          # 保留原值
    return value
```

**两处差异**：

| # | 项目 | 论文正文 | 代码实际 |
|---|---|---|---|
| **1** | x > 2 时的公式 | `⌊log2(x)⌋` | **`⌊(ln x)²⌋`** |
| **2** | x ≤ 2 时的处理 | 一律取 **1** | 保留原值（0/1/2） |

#### 差异 1 的实测证明：靠 `I1 = 44` 判定

我们不用"猜"，用**端到端实测**来定：

| 规则 | I1 能产生的不同取值数上限 | 能达到 44 吗 |
|---|---|---|
| `⌊log2(x)⌋` | 实测最大值 780 时 → **10 个**（即使最大值再放大 6 倍到 5000，也只有 13 个） | ❌ 不可能 |
| `⌊(ln x)²⌋` | 实测最大值 780 时 → **45 个** | ✅ 可以 |

**而全量数据跑出来的 `feature_map.json` 里，I1 的 vocab_size 就是 44。**

**所以代码用的是 `⌊(ln x)²⌋`，这一点无可辩驳。**

> **补充说明（诚实边界）**：这个判定对 13 个数值字段里**12 个是决定性的**，
> 但第 13 个（I10）判不了——因为它的取值极少（vocab 只有 6），
> 两种规则都能满足。所以准确表述是"**12/13 决定性排除**"，不是"13/13"。

#### 差异 2 的影响：小，但必须说

x ≤ 2 时的处理不同：

| x | 论文规则 | 代码规则 | 一样吗 |
|---|---|---|---|
| 0 | 1 | 0 | ❌ |
| 1 | 1 | 1 | ✅ |
| 2 | 1 | 2 | ❌ |

**影响评估**：这类取值在 Criteo 里占比很小（数值特征大多数 > 2），
且只影响 3 个可能的桶编号。**但它确实让最终的 vocab 与"严格按论文"不同。**

**我们的处理**：**以代码为准**（因为要复现的是作者的**实验结果**，不是论文的文字），
但这个差异在报告中明确记录。

### 4.3.4 数据集划分：8:1:1 已验证

论文没有直接说划分比例，但从三份文件的行数可以反推：

| 数据集 | train | valid | test | 比例 |
|---|---|---|---|---|
| Criteo | 36,672,493 | 4,584,062 | 4,584,062 | **80.0 : 10.0 : 10.0** |
| Avazu | 32,343,172 | 4,042,897 | 4,042,898 | **80.0 : 10.0 : 10.0** |
| iPinYou | 15,395,258 | —（无） | 4,100,716 | **78.97 : — : 21.03** |
| KKBox | 5,901,932 | 737,743 | 737,743 | **80.0 : 10.0 : 10.0** |

**Criteo / Avazu / KKBox 都是精确的 8:1:1。** iPinYou 因为无独立 valid，
test 占了约 21%。

#### 一个额外的验证：Criteo 是分层切分还是随机切分？

**这是个容易被忽略但很关键的问题**：如果切分是随机的，正负样本比例会有随机波动；
如果是**分层切分**（stratified，保证各份的正负比一致），比例会几乎相同。

**实测**：

| 分片 | 正样本数 | 总行数 | CTR |
|---|---|---|---|
| train | 9,396,350 | 36,672,493 | **25.622338%** |
| valid | 1,174,544 | 4,584,062 | **25.622341%** |
| test | 1,174,544 | 4,584,062 | **25.622341%** |

**三者差异只有 3.4×10⁻⁶ 个百分点。**

**这个差异有多小？** 若真的随机切分，一份 458 万样本、p=0.2562 的子集，
其 CTR 的抽样标准差是

```
σ = √(p(1-p)/n) = √(0.2562 × 0.7438 / 4,584,062) = 0.0204 个百分点
```

**实测差异 3.4×10⁻⁶ 个百分点，比随机切分的期望噪声小约 6000 倍。**

**结论：这不可能是随机切分，是分层切分。**

> **这条证据的价值**：它把"CTR 相等 ⇒ 分层切分"从定性判断变成了定量论证。
> 原来只能说"相同所以应该是分层切"，现在能说"差异比随机切分的期望噪声小 4 个数量级，
> 故不可能是随机切分"。**"差异很小"和"差异比应然噪声小 N 个数量级"是两个不同强度的论断。**

### 4.3.5 预处理的两道硬闸门

数据管道做完后，必须过两道检查才允许开始训练。
**这两道检查都设在训练之前**——先过闸门再跑 8 个种子，比跑完才发现参数错要省 8 倍时间。

#### 闸门①：词表总规模必须等于 910,747

```
实测 Σ(vocab_size) = 910,747
论文 Table 2        = 910,747
判定：✅ PASS（39/39 字段逐一相符）
```

#### 闸门②：由词表推出的参数量必须等于 16,532,562

```
每层交叉网络 = D×(D/2) + D/2 + D/2 + D = 195,936    （D = 39×16 = 624）
5 层 × 195,936 + (D+1) = 980,305（每个子网）
× 2 个子网 + 910,747×16 = 16,532,562
```

用这个闭式公式从词表反推参数量，与作者日志的 16,532,562 **精确相等**。

> **这个闸门的设计意图**：如果只看词表对了就开跑，万一模型结构配错了（比如层数写错），
> 会白跑 8 个种子才发现。**用词表反推参数量，能在 5 秒内确证结构与数据都对了。**

### 4.3.6 h5 格式：一个可量化的工程权衡

fuxictr 要求数据存成 h5（HDF5，一种高效的二进制容器格式）。
我们实测了存储开销：

```
每行字节数 = 39 个特征 × 8 字节（int64） + 1 个标签 × 8 字节（float64）
           = 320 字节/行
```

| 分片 | 行数 | 理论大小 | 实测大小 | 偏差 |
|---|---|---|---|---|
| train | 36,672,493 | 11,735,197,760 B | **11,735,214,144 B** | +16,384 B（0.00014%）|
| valid | 4,584,062 | 1,466,899,840 B | **1,466,916,224 B** | +16,384 B |
| test | 4,584,062 | 1,466,899,840 B | **1,466,916,224 B** | +16,384 B |

**偏差正好是 16,384 字节 = 16 KB，也就是 h5 的文件头与索引开销。**

> **一个必须说清的单位陷阱**：`ls -lh` 显示 train.h5 是 "11G"，
> 但 11,735,214,144 字节 ÷ 1024³ = **10.93 GiB**，÷ 1000³ = **11.735 GB**。
> **这两个数差 7.4%**（`11.735/10.93 − 1`），刚好落在"看起来像误差"的区间，
> 所以很容易被误当成"有压缩"或"对齐差异"，从而得出一个不存在的技术结论。
> **本文凡提文件大小，一律同时标注 GiB 与 GB。**

**关于 `int64` 的取舍**：最大词表是 C3 的 157,339，远小于 int32 上限（2.1×10⁹），
所以用 `int32` 存也完全够，体积能减半（14.67 GB → 7.33 GB）。
**我们选择 `int64` 是为了与 fuxictr 默认路径完全一致**——这是"保持原样"而非"最优选择"，
如实记录在此。
